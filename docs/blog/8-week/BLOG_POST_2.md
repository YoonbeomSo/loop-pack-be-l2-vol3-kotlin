# 대기열 구축, Kafka vs Redis -- 같은 "줄 세우기"인데 왜 기술이 다른가

부제: "Kafka도 줄 세우기 아냐?"라는 질문에 처음엔 답하지 못했습니다.

## TL;DR

- Kafka는 "넣고 나면 내 위치를 모른다" -- 순번 조회가 불가능해서 대기열에 부적합
- Redis Sorted Set은 ZRANK로 즉시 순번 조회 + SET TTL로 토큰 관리까지 단일 인프라로 해결
- Kafka는 비동기 파이프라인(주문 후), Redis는 실시간 관문(주문 전) -- 양자택일이 아니라 각자의 위치가 있다

---

## "Kafka도 줄 세우기 아냐?"

7주차에서 Kafka로 선착순 쿠폰 발급을 구현했습니다. 요청을 토픽에 넣고, Consumer가 순서대로 꺼내서 처리합니다. 분명히 "줄 세우기"입니다.

그런데 8주차 대기열도 "줄 세우기"입니다. 유저를 줄 세우고, 순서대로 입장시킵니다.

같은 건데 왜 Kafka가 아닌 Redis를 선택했을까요?

---

## 핵심 차이 -- "내 위치를 알 수 있는가"

Kafka에 메시지를 넣으면 offset이 할당됩니다. 하지만 Producer는 이 offset으로 "내 앞에 몇 명이 있는지"를 알 수 없습니다. Kafka는 Consumer가 순서대로 꺼내가는 파이프라인이지, 대기 중인 메시지의 위치를 조회하는 용도가 아닙니다.

| 요구사항 | Kafka | Redis Sorted Set |
|----------|-------|-----------------|
| 순번 조회 ("지금 몇 번째?") | 불가능 | `ZRANK` O(log N) |
| 총 대기 인원 | Consumer lag로 간접 추정 | `ZCARD` O(1) |
| 예상 대기시간 | 산출 불가 | position / TPS |
| 중복 진입 방지 | 별도 구현 필요 | `ZADD NX` 내장 |
| 토큰 관리 (TTL) | 별도 저장소 필요 | `SET EX` 내장 |

대기열은 유저가 화면 앞에서 "지금 342번째, 약 2분 후 입장"을 보는 시나리오입니다. 실시간 피드백이 핵심인데, Kafka는 이걸 제공할 수 없습니다.

---

## 각자의 자리 -- 주문 전 vs 주문 후

정리하면, 둘은 양자택일이 아니라 파이프라인의 서로 다른 위치에 있습니다.

```
[유저] → [Redis 대기열] → [주문 API] → [Kafka 이벤트 파이프라인]
          (주문 전, 관문)                  (주문 후, 비동기 처리)
```

| 구분 | Redis 대기열 (R8) | Kafka 파이프라인 (R7) |
|------|-------------------|----------------------|
| 위치 | 주문 API 앞단 | 주문 API 뒷단 |
| 목적 | 트래픽 조절 + 유저 피드백 | 이벤트 전파 + 비동기 처리 |
| 유저 인지 | "342번째입니다" (실시간) | 유저 모름 (백엔드 내부) |
| 유실 시 영향 | 줄 서있던 유저 소멸 | 후속 처리(집계, 쿠폰) 누락 |
| 내구성 요구 | 낮음 (일시적 상태) | 높음 (비즈니스 이벤트) |

---

## 그러면 Kafka로 대기열을 만들 수는 없는 건가?

완전히 불가능한 건 아닙니다. 하지만 Kafka 단독으로는 부족하고, 보조 저장소가 필요합니다.

예를 들어 Kafka에 진입 요청을 넣고, Consumer가 소비하면서 Redis나 DB에 순번 정보를 기록하면 순번 조회는 가능합니다. 하지만 이 경우 Kafka는 "메시지 큐" 역할만 하고, 실제 대기열 상태 관리는 Redis/DB가 합니다.

결국 Redis Sorted Set 하나로 끝나는 걸, Kafka + Redis 두 개를 조합해서 하는 셈입니다. 복잡도만 올라가고 얻는 게 없습니다.

---

## 마무리

> 기술 선택은 기능이 아니라 시나리오에 맞춰야 한다.

Kafka와 Redis는 둘 다 "줄 세우기"를 할 수 있지만, "유저가 자기 순번을 알아야 하는가?"라는 한 가지 질문으로 답이 갈립니다. 같은 버퍼링이라도 유저 경험에 따라 적합한 기술이 완전히 달라진다는 걸 이번 과제에서 배웠습니다.
