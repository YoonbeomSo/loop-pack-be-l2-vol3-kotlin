## 멘토링 전 학습 — 팀원 질문 분석

### 팀원 질문의 공통 키워드 3가지

1. **캐시 무효화가 어렵다** — 거의 모든 사람이 고민
2. **DB와 캐시의 정합성은 완벽할 수 없다** — 어디까지 허용하냐
3. **인덱스만으로 충분한 건 아닌가** — 캐시 복잡도 대비 효과

### P0-1. 박수환: "인덱스, 비정규화, 캐시를 동시에 적용할 때 반드시 필요하다는 판단 기준"

**질문 해석**:
이번 과제에서 인덱스, 비정규화(likeCount 컬럼), Redis 캐시를 세 가지 다 적용했다. 그런데 이 세 개가 서로 겹치는 부분이 있어서 의문이 든다.
- 캐시가 잘 동작하면 DB 쿼리 자체를 안 타니까, 인덱스를 최적화해봤자 체감이 안 됨
- 비정규화된 likeCount와 캐시가 동시에 존재하면, DB의 likeCount는 맞는데 캐시에는 옛날 값이 남아있는 상태가 생김 → 관리 포인트가 늘어남
- 궁금한 것:
  1. 실무에서 "인덱스로 충분 → 비정규화 추가 → 캐시" 순서로 단계적 도입하는지, 처음부터 캐시까지 같이 설계하는지
  2. 10만건 규모에서 "아직 캐시는 필요 없다"고 판단할 수 있는 기준이 있는지 (QPS 몇 이상부터 캐시를 고려한다든지)
  3. 세 가지를 다 적용한 상태에서 나중에 하나를 빼야 할 때 빼기 쉬운 구조를 만드는 팁

**핵심을 한 줄로**: 세 가지 최적화가 서로 겹치는데, 각각이 **언제 필요해지는지의 판단 기준**이 뭐냐?

```
캐시 hit → DB 안 침 → 인덱스 효과 체감 불가
캐시 miss → DB를 침 → 이때 인덱스가 필요
비정규화 → likeCount를 미리 저장해서 JOIN 제거 → 캐시와 값 불일치 가능
```

**Claude 답변**:

실무에서는 **단계적으로 도입하는 것이 원칙**이다.

```
1단계: 인덱스 최적화 (비용 거의 0, 효과 큼)
   → EXPLAIN 돌려보고 Full Scan이면 인덱스 추가
   → 이것만으로 해결되면 여기서 끝. 대부분의 서비스는 여기서 충분

2단계: 비정규화 (비용 중간)
   → JOIN + GROUP BY가 병목일 때
   → likeCount처럼 자주 조회되는 집계값을 미리 저장
   → trade-off: 쓰기 복잡도가 올라감 (좋아요 추가/취소 시 likeCount도 동기화해야 함)

3단계: 캐시 (비용 높음, 효과 가장 큼)
   → 인덱스 + 비정규화로도 QPS를 못 버틸 때
   → DB 커넥션 풀이 고갈될 정도의 트래픽일 때
   → trade-off: 무효화 전략, 정합성 관리, 인프라 운영 비용 추가
```

**"아직 캐시가 필요 없다"의 판단 기준**: 정확한 QPS 수치보다는 **증상**을 보고 판단한다.
- DB 커넥션 풀 대기 시간이 늘어남
- 슬로우 쿼리 로그에 동일한 조회 쿼리가 반복적으로 찍힘
- 같은 데이터를 같은 조건으로 반복 조회하는 패턴이 모니터링에 보임
- 10만건 + 인덱스면 조회가 수 ms. **초당 수천 요청이 아니면 캐시 없이도 충분**.

**빼기 쉬운 구조의 핵심**: 캐시 로직을 `ProductCacheRepository`라는 별도 클래스로 분리하면, 캐시를 빼고 싶을 때 Service에서 캐시 호출 2~3줄만 제거하면 됨. `@Cacheable` 어노테이션은 AOP라 흐름이 숨겨져서 오히려 빼기 어려울 수 있음.

```kotlin
// 캐시 있을 때
fun getProductInfo(productId: Long): ProductInfo {
    productCacheRepository.getProductDetail(productId)?.let { return it }  // ← 이 줄
    val info = ProductInfo.from(getProduct(productId))
    productCacheRepository.setProductDetail(productId, info)               // ← 이 줄
    return info
}

// 캐시 빼고 싶을 때 → 위 두 줄만 삭제하면 끝
fun getProductInfo(productId: Long): ProductInfo {
    return ProductInfo.from(getProduct(productId))
}
```

**멘토님 답변**:

실무에서는 **로컬 캐시(서버 메모리)와 원격 캐시(Redis)를 함께 쓰는 2-tier 구조**가 일반적이다.

```
요청 → 로컬 캐시(서버 메모리) → 원격 캐시(Redis) → DB
         ↑ 갱신 주기 짧게           ↑ TTL 길게
```
> **로컬 캐시**: 서버 프로세스 안의 HashMap이나 Caffeine 같은 인메모리 캐시.
> 네트워크 호출 없이 바로 메모리에서 읽으니 가장 빠름.
> 단점은 서버가 여러 대면 각 서버마다 다른 값을 가질 수 있다는 것.
> 그래서 갱신 주기를 짧게(수 초~수십 초) 잡아 최신성을 유지한다.

- 로컬 캐시가 원격 캐시(Redis)를 바라보는 구조로, **로컬 캐시 갱신 주기를 짧게** 설정하여 최신성을 유지
- 캐시 적용 범위는 **브랜드별 약 50개 카테고리, 각 카테고리별 3페이지 정도만 캐시**하고, 필터가 걸린 페이지는 캐시하지 않음
- 개인화 데이터는 캐시 효율이 낮으므로 **클라이언트 사이드 캐시**를 활용하거나 부분 캐싱 전략을 사용
- 각 데이터 필드별로 **캐시 무효화 주기를 다르게** 설정하는 전략도 있음 (가격은 짧게, 설명은 길게)
- TTL 없이 긴 캐시를 유지한 후 **라이트 쓰루(Write-Through) 방식으로 갱신**하는 경우도 있음

> **라이트 쓰루(Write-Through)**: DB에 쓸 때 캐시도 동시에 갱신하는 방식.
> 반대 개념인 Cache-Aside는 "읽을 때 없으면 채운다"지만, Write-Through는 "쓸 때 미리 채운다".
> 캐시가 항상 최신이라는 장점이 있지만, 쓰기 시점에 캐시 업데이트 비용이 추가된다.

### P0-2. 박수환: "DB 트랜잭션과 캐시 연산의 원자성 불일치를 실무에서 어떤 철학으로 다루는지"

**질문 해석**:
현재 `LikeFacade.like()`에서 `@Transactional` 내부에서 캐시를 삭제하고 있다. 그런데 Redis와 DB는 같은 트랜잭션으로 묶이지 않기 때문에, 캐시를 삭제하는 시점에 따라 불일치가 발생한다.
- 트랜잭션 안에서 삭제하면: 커밋 전에 다른 요청이 아직 반영 안 된 DB 데이터를 읽어서 캐시에 다시 넣을 수 있음
- `@TransactionalEventListener(AFTER_COMMIT)`으로 커밋 후에 삭제하면: 커밋~삭제 사이의 짧은 구간에서 stale 캐시를 읽을 가능성이 여전히 남음
- **어느 쪽이든 완벽하게 일치시킬 수는 없다**는 걸 알겠는데, 실무에서 이걸 어떻게 다루냐?
- 궁금한 것:
  1. likeCount처럼 크리티컬하지 않은 값은 TTL 자연 만료로 허용하고 있는데, 실무에서도 데이터 성격에 따라 허용 범위를 나누는지
  2. 크리티컬한 값이라면 캐시 무효화 시점을 어떻게 잡는지 (AFTER_COMMIT? 아예 캐시 안 쓰기?)

**추가 시나리오 — Redis put ack 실패와 PG API 응답 실패**:
```kotlin
@Transactional
상품업데이트() {
    productRepository.save();
    redisTemplate.put("product-100", json);
      // <-- ack를 못받으면?
}

// pg업데이트가 포함되면 트랜잭션이 길어진다..

@Transactional
placeOrder() {
    orderRepo.save();
    pgApi.pay(); // 여기서는 성공하는데.. 응답만 모종의 이슈로 못받으면..
}
```
- **Redis put ack 실패**: 트랜잭션 안에서 Redis에 값을 넣었는데 ack를 못 받으면, DB에는 저장됐지만 캐시에는 반영 안 된 상태가 됨. 예외가 발생하면 트랜잭션 롤백되어 DB도 원복되지만, Redis에 이미 값이 들어간 경우 Redis만 남는 불일치 발생 가능
- **PG API 응답 실패**: PG에서 실제 결제는 성공했는데 네트워크 문제로 응답을 못 받으면, 트랜잭션이 롤백되어 주문이 없는데 결제는 된 상태가 됨. 이것이 "외부 시스템과의 원자성 불일치"의 전형적인 예시

**핵심을 한 줄로**: DB와 캐시는 **별개 시스템이라 원자성이 없는데**, 이 불일치 윈도우를 어디까지 허용하냐?

**시간 순서로 보는 두 가지 방법**:

**방법 A: 트랜잭션 안에서 캐시 삭제** — 심각한 문제 발생 가능
```
시간  요청A (좋아요 누름)              요청B (상품 조회)
─────────────────────────────────────────────────
t1   BEGIN
t2   UPDATE likeCount = 101
t3   캐시 삭제 (DELETE key)
t4                                    캐시 miss → DB 조회
t5                                    DB: READ COMMITTED → 커밋 전이라 100 읽음
t6                                    likeCount=100을 캐시에 저장
t7   COMMIT (DB는 101)
t8   결과: DB=101, 캐시=100 ❌ (TTL 만료까지 유지)
```

**방법 B: AFTER_COMMIT으로 캐시 삭제** — 찰나의 불일치만 존재
```
시간  요청A (좋아요 누름)              요청B (상품 조회)
─────────────────────────────────────────────────
t1   BEGIN
t2   UPDATE likeCount = 101
t3   COMMIT 완료 (DB=101)
t4                                    캐시 hit → 100 반환 (아직 삭제 전)
t5   AFTER_COMMIT 이벤트 → 캐시 삭제
t6                                    다음 요청 → 캐시 miss → DB 101 읽음 ✅
결과: t4에서 잠깐(수 ms) 옛날 값이 보임, t5 이후 정상
```

**Claude 답변**:

실무에서는 **데이터 성격에 따라 전략을 명확히 나눈다**.

| 데이터 성격 | 예시 | 캐시 전략 | 이유 |
|------------|------|----------|------|
| **일어도 상관없음** | 좋아요 수, 조회수 | TTL 자연 만료 or AFTER_COMMIT | 501이 500으로 보여도 사용자가 모름 |
| **짧은 시간은 허용** | 상품 정보 (이름, 설명) | AFTER_COMMIT으로 즉시 무효화 | 수정 후 수 ms 내에 반영되면 충분 |
| **절대 틀리면 안 됨** | 재고, 결제 금액, 잔액 | **캐시 자체를 안 함** | 초과 판매, 이중 결제 등 금전 사고 |

**실무 원칙**: "이 값이 1분 동안 틀리면 돈이 날아가는가?"
- Yes → 캐시 안 함. 항상 DB에서 실시간 조회
- No → TTL이나 AFTER_COMMIT으로 "대부분 맞고, 아주 가끔 짧은 시간 틀릴 수 있음"을 허용

**크리티컬한 값의 실무 패턴**:
- 재고: 캐시는 "참고용" (화면에 "재고 있음/없음"만 표시), 실제 차감은 항상 DB에서 `FOR UPDATE`로 정확히
- 결제: 절대 캐시 안 함
- 포인트/잔액: Redis 자체를 저장소로 쓰는 경우도 있음 (DECR이 원자적이니까), 이 경우 DB와 주기적 동기화

**추가 시나리오에 대한 해석**:

**Redis put ack 실패**: 실무에서는 Redis 실패를 **try-catch로 감싸서 무시**하는 것이 일반적이다. 캐시는 "있으면 좋고, 없으면 DB에서 읽으면 됨"이므로, Redis 장애가 비즈니스 트랜잭션을 롤백시키면 안 된다. Redis에 값이 이미 들어갔는데 ack만 못 받은 경우는 TTL로 자연 정리된다.

**PG API 응답 실패**: 이건 캐시 문제가 아니라 **분산 트랜잭션 문제**이다. 실무에서는:
- 주문을 "결제 대기" 상태로 먼저 저장 → PG 호출 → 성공 시 "결제 완료"로 상태 변경 (Saga 패턴)
- PG 응답을 못 받으면 → PG사의 결제 조회 API로 **멱등성 키 기반 조회**를 해서 실제 결제 여부 확인
- 트랜잭션 안에 외부 API 호출을 넣으면 안 됨 → 트랜잭션이 외부 API 응답 시간만큼 길어져서 커넥션 풀 고갈 위험

**멘토님 답변**:

핵심 메시지: **실무에서는 불일치를 기본적으로 허용한다.**

- 같은 VPC 내에서 네트워크 장애 확률이 낮고, 서버 순단도 매우 짧아서 **체감하기 어려운 수준**
- **조회형 캐시**(Cache-Aside로 "읽을 때 채우는" 방식)는 저장 실패해도 큰 리스크가 없음 → 다음 요청에서 DB에서 다시 읽어 채우면 되니까

> **VPC(Virtual Private Cloud)**: AWS 같은 클라우드에서 내 서비스들만 사용하는 가상 사설 네트워크.
> 같은 VPC 안에서는 Redis, DB가 물리적으로 가까워서 네트워크 장애 확률이 매우 낮다.

불일치 허용 범위 설정과 캐시 업데이트 방식:
- **라이트 쓰루 캐시**: 도메인 이벤트를 발행하고, 컨슈머가 반복 수행하여 캐시를 보장하는 방법이 있지만 실무에서는 잘 사용하지 않음
- **배치/업**을 통해 캐시를 완벽히 채우는 경우도 있으나, 대부분은 어느 정도 불일치를 허용하는 실무적 타협을 함
- **큐를 통한 캐시 업데이트**는 분산 트랜잭션이므로 캐시 저장 시점이 예측 불가능해지는 단점이 있음

> **컨슈머(Consumer)**: 메시지 큐(Kafka 등)에서 메시지를 꺼내서 처리하는 서비스.
> "도메인 이벤트 발행 → 컨슈머가 반복 수행"이란, 상품 수정 이벤트를 Kafka에 보내면
> 별도 서비스가 그 이벤트를 읽어서 캐시를 갱신하는 구조를 말한다.

캐시 무효화 전략:
- **라이크 파사드 패턴**: 업데이트 시 캐시 키를 삭제하고, 다음 조회 시 DB에서 다시 채우는 방식이 가장 많이 사용됨
- 이 방식은 캐시 메모리 낭비를 줄이지만, **삭제 직후 다수 요청이 몰리면 DB에 캐시가 물릴 수 있음** (Cache Stampede)
- `@TransactionalEventListener(AFTER_COMMIT)` 시점에 캐시 삭제를 수행하면 불일치 가능성을 줄일 수 있음

DB 레플리카 사용 시 주의점:
- **리드 모디파이(Read-Modify-Write) 패턴**에서 읽기를 슬레이브(레플리카)로 하면 데이터 꼬임 장애 발생 가능

> **리드 모디파이 패턴**: "값을 읽고 → 수정해서 → 다시 저장"하는 흐름.
> 예: 재고를 읽고(10개) → 1개 빼서(9개) → 저장. 이때 "읽기"를 레플리카에서 하면
> 복제 지연 때문에 옛날 값(아직 11개)을 읽을 수 있고, 잘못된 값으로 저장하게 된다.
> 그래서 수정이 따라오는 읽기는 **반드시 마스터 DB에서** 해야 한다.

### P0-3. 박수환: "목록 노출 캐시가 복잡도 대비 효과가 있는가"

**질문 해석**:
목록 캐시 키를 `product:list:{brandId}:{sortType}:{page}:{size}`로 설계했는데, 조합이 꽤 많아진다.
- 현재: 브랜드 20개 × sort 3개 × page × size = 수천 개 키
- 필터 조건이 추가되면 키가 기하급수적으로 증가
- 좋아요 1건 변경 때마다 전부 evict하면 캐시가 항상 비어있어서 의미 없음
- 그래서 evict 없이 TTL 3분 자연 만료에만 의존하고 있음
- 궁금한 것:
  1. 복합 인덱스가 이미 잘 동작하는 상태에서 목록 캐시까지 두는 게 관리 복잡도만 올리는 건 아닌지
  2. 목록 캐시를 쓴다면 키 조합이 커지는 것을 관리하는 실무적인 패턴

**핵심을 한 줄로**: 인덱스만으로 충분한 상황에서 **목록 캐시는 오버엔지니어링 아닌가?**

**키 폭발 문제를 숫자로 보면**:
```
현재: brandId(21) × sort(3) × page(50) × size(1) = 3,150개 키
필터 추가 시: + 가격대(5) × 카테고리(10) = 315,000개 키
→ 좋아요 1번 → 좋아요순 정렬 영향 → 수십만 개 캐시 중 어떤 게 영향받는지 모름
```

**Claude 답변**:

목록 캐시는 **"변경 빈도가 낮고, 같은 조건의 반복 조회가 많은 데이터"에만 효과적**이다.

| 데이터 | 변경 빈도 | 목록 캐시 효과 |
|--------|----------|--------------|
| 카테고리 목록 | 거의 안 바뀜 | 매우 효과적 |
| 브랜드 목록 | 가끔 바뀜 | 효과적 |
| 공지사항 목록 | 하루 몇 번 | 효과적 |
| 좋아요순 상품 목록 | 좋아요가 수시로 바뀜 | **효과 의문** |
| 실시간 랭킹 | 계속 바뀜 | **효과 없음** |

현재 과제 상황에서 솔직한 판단:
- 10만건 + 복합 인덱스 → 조회 수 ms → **인덱스만으로 충분**할 가능성 높음
- 목록 캐시는 **학습 목적으로 의미가 있지만**, 실무적으로 이 규모에서는 인덱스가 더 중요

**실무에서 목록 캐시를 쓴다면**:
1. **TTL에만 의존** (evict 안 함) — 가장 단순하고 현실적. "5분간 옛날 순서가 보여도 되는가?" → 대부분 OK
2. **인기 조합만 캐시** — 전체+최신순, 전체+인기순 등 TOP 5 조합만. 나머지는 DB 직접 조회
3. **캐시 키에 버전** — `product:list:v42:brand=1:sort=LATEST:page=0`. 변경 시 버전만 43으로 올리면 v42 키는 자연 만료

**멘토님 답변**:

실무에서 목록 캐시의 실제 운영 사례:
- **브랜드별 3페이지 정도만 캐시**하며, **필터별 캐시는 하지 않음** — 필터 없는 기본 페이지에 집중
- 개인화 데이터는 캐시 효율이 낮아 **클라이언트 사이드 캐시를 활용**하거나 부분 캐싱 전략을 사용
- **캐시 키 개수보다 캐시 데이터 총량을 계산하는 습관이 중요** — "키가 3,000개"보다 "총 50MB"가 의사결정에 더 유용

> **클라이언트 사이드 캐시**: 서버(Redis)가 아니라 브라우저나 앱 자체에서 캐시하는 것.
> 예를 들어 "최근 본 상품"이나 "내가 검색한 필터 조합" 같은 개인화 데이터는
> 사용자마다 다르니까 서버에서 캐시해도 hit율이 낮다.
> 대신 브라우저 localStorage나 앱 메모리에 저장하면 네트워크 호출 자체를 줄일 수 있다.

- Redis 키 제한은 존재하지만 실무에서 쉽게 초과하지 않음
- 캐시 대상 모델(DTO)이 변경되면 **캐시 키도 반드시 업데이트**해야 하며, 이를 놓치면 장애 발생률이 높음 — 필드가 추가됐는데 옛날 캐시에는 그 필드가 없어서 NPE 발생

### P0-4. 안유진: "Soft Delete에서의 인덱스 설계"

**질문 해석**:
모든 읽기 쿼리에 `deleted_at IS NULL` 조건이 붙는다. 상품 목록 조회의 경우:
```sql
WHERE deleted_at IS NULL AND brand_id = ? ORDER BY price ASC
```
soft delete 필터 + 비즈니스 필터 + 정렬이 조합되는데, 복합 인덱스를 `(brand_id, price, deleted_at)`로 잡아야 하는지, `(brand_id, price)`로 잡고 deleted_at은 별도 필터로 처리해야 하는지 판단이 어렵다.
- deleted_at IS NULL은 **카디널리티가 극단적으로 낮음** (대부분 NULL)
- 이런 "거의 모든 행이 같은 값"인 조건이 복합 인덱스 선두에 오면 오히려 비효율적이지 않나?

**안유진 본인의 EXPLAIN ANALYZE 실험**:
직접 데이터를 생성해서 두 인덱스를 비교 실험했다.
- `(brand_id, price, deleted_at)` vs `(brand_id, price)`
- 테스트 환경: deleted_at이 대부분 NULL인 상황(약 99%)
- `EXPLAIN ANALYZE`로 실행 계획을 확인한 결과, 옵티마이저는 `(brand_id, price)` 인덱스를 사용하는 경우가 더 효율적이었고, `(brand_id, price, deleted_at)` 인덱스는 deleted_at 조건의 선택도가 낮아 실제 필터링에 거의 기여하지 않는 것으로 나타남
- 다만 데이터 분포나 삭제 비율이 달라지면 결과가 달라질 수 있어, 실무 기준이 궁금하다는 질문

**핵심을 한 줄로**: 카디널리티가 극단적으로 낮은 `deleted_at IS NULL`을 **인덱스의 어디에 둬야 하냐?**

**Claude 답변**:

안유진의 실험 결과가 정확하다. `deleted_at`은 **인덱스에 포함시키더라도 효과가 거의 없다**.

인덱스의 효과는 **데이터를 많이 걸러낼수록** 좋다. `deleted_at IS NULL`이 99%라면 거의 못 거른다.

```
(brand_id, price, deleted_at) 인덱스가 동작하는 순서:
1. brand_id = 1 → 5,000건으로 줄어듦 (핵심 필터)
2. price 순 정렬 (이미 인덱스에 정렬되어 있으므로 filesort 불필요)
3. deleted_at IS NULL → 5,000건 안에서 후필터 (어차피 대부분 통과)
→ deleted_at이 인덱스에 있어도 거의 기여하지 않음 (안유진 실험 결과와 일치)

(brand_id, price) 인덱스가 동작하는 순서:
1. brand_id = 1 → 바로 5,000건으로 줄어듦 (핵심 필터)
2. price 순 정렬 (이미 인덱스에 정렬되어 있으므로 filesort 불필요)
3. deleted_at IS NULL → 5,000건 안에서 후필터 (어차피 대부분 통과)
→ 결과적으로 동작이 거의 동일. 인덱스 크기만 줄어들어 이쪽이 더 효율적
```

**실무 기준**: "이 조건이 전체 데이터의 30% 이상을 걸러내는가?"
- Yes (예: `brand_id = 1` → 95% 걸러냄) → 인덱스에 포함, 선두에 배치
- No (예: `deleted_at IS NULL` → 1%만 걸러냄) → 인덱스에서 빼고 후필터로 처리

추가로, MySQL 옵티마이저는 통계 정보를 보고 `deleted_at IS NULL`이 대부분인 걸 알면 그 조건의 인덱스 사용을 건너뛰기도 함. **비즈니스 필터(brand_id)가 훨씬 효과적인 필터 역할을 한다**.

Partial Index(부분 인덱스)를 지원하는 DB(PostgreSQL)라면 `WHERE deleted_at IS NULL` 조건의 인덱스를 만들 수 있지만, **MySQL은 Partial Index를 지원하지 않음**.

**멘토님 답변**:

- **소프트 딜리트 필터는 일반적으로 인덱스에 포함하지 않음** — Claude 답변 및 안유진 실험 결과와 동일한 결론
- 인덱스 설계는 **필터와 정렬 컬럼 위주**로 하되, 카디널리티가 극단적으로 낮은 조건은 후필터로 처리하는 것이 원칙

### P0-5. 안유진: "정렬 옵션이 여러 개일 때 인덱스 전략"

**질문 해석**:
상품 목록 조회에 3가지 정렬이 있다:
- LATEST → `(brand_id, id DESC)` 또는 PK 활용
- PRICE_ASC → `(brand_id, price ASC)`
- POPULAR → `(brand_id, like_count DESC, id DESC)`

각각 최적의 복합 인덱스가 다르다. 정렬 옵션마다 인덱스를 하나씩 만들면 쓰기 성능이 저하된다.
- 인덱스 3개 → INSERT 1건 → 테이블 1번 + 인덱스 3번 = 4번 쓰기
- 궁금한 것: 실무에서 정렬 옵션별로 인덱스를 각각 만드는지, 가장 빈번한 정렬 하나만 인덱스 걸고 나머지는 Using filesort를 감수하는지

**핵심을 한 줄로**: 인덱스 3개의 **읽기 이득 vs 쓰기 비용**을 어떻게 판단하냐?

**Claude 답변**:

**읽기/쓰기 비율로 판단한다.**

```
상품 테이블의 현실적인 트래픽:
- 읽기: 초당 1,000번 (목록 조회, 상세 조회)
- 쓰기: 하루 100번 (상품 등록/수정) → 초당 0.001번
- 읽기:쓰기 비율 = 1,000,000:1

→ 인덱스 3개 만드는 게 명백히 이득
```

인덱스 쓰기 비용 자체도 크지 않다. B-Tree에 노드 하나 추가하는 건 O(log n)이라, 10만건이어도 5~6번 비교면 끝.

**실무에서의 판단 프로세스**:
1. **정렬 옵션별 사용 비율을 로그로 확인**
   - 최신순 60%, 가격순 30%, 좋아요순 10% → 셋 다 인덱스
   - 최신순 95%, 가격순 4%, 좋아요순 1% → 최신순만 인덱스, 나머지 filesort 감수
2. **80% 이상 사용되는 정렬은 인덱스 생성**
3. **5% 미만 사용되는 정렬은 filesort 감수** (인덱스 유지 비용 > 이득)
4. **테이블의 쓰기 빈도도 함께 고려**
   - 좋아요 테이블: 읽기 초당 100, 쓰기 초당 50 → 인덱스 신중하게
   - 상품 테이블: 읽기 초당 1000, 쓰기 하루 100 → 인덱스 부담 없음

참고: `like_count`는 좋아요마다 UPDATE되므로, `(brand_id, like_count DESC)` 인덱스가 자주 갱신됨. 하지만 B-Tree 갱신은 O(log n)이라 10만건 규모에서는 무시 가능한 수준.

**멘토님 답변**:

- **복합 인덱스를 적극적으로 사용하지 않는 편** — 레퍼런스 ID(FK)와 정렬 컬럼 위주로 인덱스를 설계
- **정렬에 사용되는 컬럼은 반드시 인덱스를 걸어야** 슬로우 쿼리를 방지할 수 있음 — filesort가 발생하면 데이터가 많아질수록 급격히 느려지기 때문
- 필터 조건이 많거나 데이터가 많은 경우에는 인덱스 설계에 **더 신중**해야 함

> **레퍼런스 ID(FK)**: 다른 테이블을 참조하는 외래 키.
> 예: `products.brand_id`는 brands 테이블을 가리키는 FK.
> `WHERE brand_id = ?`처럼 FK로 필터링하는 쿼리가 매우 빈번하므로
> FK 컬럼에 인덱스를 거는 것은 거의 필수적이다.

### P0-6. 서태수: "RDB 환경에서 목록 조회 성능 개선 — Redis TTL 캐시 vs Materialized View"

**질문 해석**:
실무에서 상품 목록은 ES로 많이 쓴다고 알고 있다. 하지만 ES 도입 전이거나 RDB만으로 해결해야 하는 상황이 이번 과제.
- 목록에 Redis 캐시를 적용하려니 `brandId × sortType × page` 조합으로 키가 폭발
- 상품 수정 시 해당 상품이 포함된 캐시 키를 특정할 수 없어서 선택적 무효화가 불가능
- TTL에만 의존해야 하는데, 그러면 차라리 Materialized View(MV)로 읽기 전용 테이블을 만들고 비동기 이벤트로 갱신하는 게 낫지 않나?
- 궁금한 것: RDB만으로 버텨야 하는 상황에서 어떤 순서로 접근하는지

**핵심을 한 줄로**: 목록 캐시의 키 폭발 + 무효화 불가 문제 → **읽기 전용 테이블(MV)이 더 현실적이지 않냐?**

**Materialized View란?**:
```
일반 View: SELECT 할 때마다 JOIN 실행 (가상 테이블)
MV: 쿼리 결과를 실제 테이블로 저장해둠 → 읽기 빠름, 갱신은 별도

MySQL에서의 MV (네이티브 미지원, 직접 구현):
1. 읽기 전용 테이블 생성 (product_list_view)
2. 상품 변경 이벤트 → 비동기로 이 테이블 갱신
3. 목록 조회는 이 테이블에서 읽음
```

**Claude 답변**:

RDB만으로 버텨야 할 때의 현실적인 순서:

```
1. 인덱스 최적화 → 거의 항상 이것만으로 충분
2. 비정규화 → JOIN이 병목일 때 (likeCount 컬럼 추가 등)
3. 목록 캐시 TTL → 같은 조건의 반복 조회가 압도적으로 많을 때
4. MV (읽기 전용 테이블) → 여기까지 오면 보통 ES 도입을 고려하는 게 맞음
```

**MV가 Redis 캐시보다 반드시 나은 건 아니다**:
- Redis 캐시: miss 나면 DB에서 읽으면 됨 (fallback 존재). 캐시가 빈 상태에서도 서비스는 동작.
- MV: MV 자체가 틀리면(갱신 누락) 틀린 데이터를 계속 줌. 원본 테이블과의 정합성을 별도로 관리해야 함.
- MV는 **"원본 테이블과 MV 두 개를 유지관리"해야 하는 부담**이 있음. "어느 쪽이 진짜냐?" 문제가 생김.

**현실적 판단**:
- 현재 규모(10만건, 인덱스 있음) → 1~2단계로 충분
- 트래픽이 많아져서 DB가 못 버티면 → Redis TTL 캐시 (가장 단순)
- 검색이 핵심 기능이 되면 → ES 도입을 고려 (MV보다 ES가 낫다)

**멘토님 답변**:

- **MV를 사용하면 선택적 무효화가 가능**하지만, MV 자체에도 인덱스 설계가 필수적임
- TTL 캐시는 무효화가 어려워서, **MV나 읽기 전용 테이블 구조가 더 나은 경우**도 있음
- 실무에서 대규모 트래픽 처리: **레플리카 DB와 Redis 캐시 조합으로 수백만 MAU도 충분히 처리 가능**
- Redis 클러스터 구조로 고가용성 및 부하 분산 구현

> **MAU(Monthly Active Users)**: 한 달간 서비스를 사용한 순 사용자 수.
> "수백만 MAU"라 하면 초당 수천~수만 요청이 발생하는 규모인데,
> 레플리카 DB(읽기 분산) + Redis 캐시(DB 안 침)를 조합하면 이 정도 트래픽은 감당할 수 있다는 뜻.

> **Redis 클러스터**: Redis 서버 여러 대를 묶어서 운영하는 구조.
> 데이터를 여러 노드에 분산 저장(샤딩)하고, 한 노드가 죽어도 다른 노드가 대체(고가용성)한다.
> 단일 Redis는 메모리와 처리량에 한계가 있지만, 클러스터로 수평 확장이 가능하다.

### P1-1. 박수환: "시드 데이터 분포와 EXPLAIN 결과"

**질문 해석**:
과제에서 "각 컬럼의 값은 다양하게 분포하도록" 하라고 했는데, 현재 시드 데이터는 brandId를 20개 브랜드에 **균등 분배**(브랜드당 5,000건)했다.
- 실제 서비스에서는 특정 브랜드(나이키)에 상품이 몰려 있는 경우가 많음
- 편향 분포에서는 옵티마이저가 "50%나 읽을 거면 인덱스보다 Full Scan이 낫겠다"고 판단할 수 있음
- 궁금한 것:
  1. 실무에서 실제 서비스 유사한 분포를 어떻게 만드는지 (운영 DB 통계를 뽑는지, 최악 케이스를 가정하는지)
  2. EXPLAIN의 rows 추정이 실제와 크게 차이날 때 해결 방법
  3. 시드 데이터를 넣는 방식 (SQL 프로시저 vs Spring Batch vs JDBC batchUpdate)

**핵심을 한 줄로**: **균등 분포에서 잘 타는 인덱스가, 편향 분포에서도 잘 탈까?**

```
균등 분포: 브랜드 20개 × 5,000건 → brand_id = 1 조회 → 5% → 인덱스 잘 타
편향 분포: 나이키 50,000건 → brand_id = 나이키 → 50% → 옵티마이저가 Full Scan 선택 가능
```

**Claude 답변**:

**1. 실무에서 인덱스 검증 시 데이터 분포**:
- 운영 DB에서 `SELECT brand_id, COUNT(*) FROM products GROUP BY brand_id`로 실제 분포 확인
- **가장 많은 브랜드(최악 케이스)로 EXPLAIN 돌림** — 최선이 아니라 최악에서 동작해야 하니까
- `ANALYZE TABLE products` 실행으로 옵티마이저 통계를 최신으로 갱신 후 테스트
- 테스트 데이터는 "균등 + 편향 혼합"이 현실적 (상위 5개 브랜드에 60%, 나머지 15개에 40%)

**2. EXPLAIN rows 추정이 실제와 다를 때**:
- `ANALYZE TABLE`로 통계 갱신 (옵티마이저가 사용하는 통계가 오래된 경우)
- `FORCE INDEX(idx_name)`으로 강제 지정해서 실제 성능 비교 (옵티마이저 판단이 틀렸는지 확인)
- `EXPLAIN ANALYZE` (MySQL 8.0.18+) → 실제 실행 시간까지 측정 (EXPLAIN은 추정, EXPLAIN ANALYZE는 실측)

**3. 시드 데이터 넣는 방식**:
| 방식 | 속도 | 특징 |
|------|------|------|
| SQL 프로시저 | 중간 | 가장 간단, DB 안에서 완결 |
| JDBC batchUpdate | 중간 | 애플리케이션에서 제어 가능, 복잡한 로직 |
| `LOAD DATA INFILE` | **가장 빠름** | CSV → DB 직접 로드, 10만건 수초 |
| 운영 DB 덤프 마스킹 | - | 실무에서 가장 현실적, 실제 분포 그대로 |

**멘토님 답변**:

- **운영 데이터 스냅샷을 활용해 테스트 데이터를 구성하는 방식을 선호** — 실제 분포가 그대로 반영되니까
- 법적 문제가 없으면 **실제 운영 데이터를 테스트 환경에 복제**하는 것이 가장 정확

> **데이터 스냅샷**: 특정 시점의 DB 전체 상태를 복사해둔 것.
> AWS RDS라면 자동 백업 스냅샷이 있고, 이걸 테스트 환경에 복원하면
> 실서비스와 동일한 데이터로 인덱스 성능을 검증할 수 있다.
> 단, 개인정보가 포함되어 있으면 마스킹(이름→"***", 전화번호→"010-****-1234")이 필요하다.

- 대용량 데이터는 **샘플링**하여 테스트 데이터 구성 — 100만건 중 10만건만 뽑아도 분포 비율은 유지됨
- 편향된 데이터 분포 시 **힌트(FORCE INDEX 등)**를 사용해 쿼리 플랜을 조정한 경험 공유

> **힌트(Query Hint)**: 옵티마이저에게 "이 인덱스를 써라"고 강제 지시하는 것.
> 옵티마이저가 통계 기반으로 잘못된 판단을 할 때(편향 분포에서 Full Scan 선택 등)
> `SELECT * FROM products FORCE INDEX(idx_brand_price) WHERE ...`처럼 강제 지정할 수 있다.
> 단, 데이터가 변하면 힌트가 오히려 성능을 악화시킬 수 있어 주의가 필요하다.

### P1-2. 안유진: "목록 캐시의 무효화 문제"

**질문 해석**:
상품 상세(`product:42`)는 캐시 키가 명확하고 evict가 쉽다. 그런데 목록 캐시는 brandId, sortType, page, size 조합에 따라 키가 폭발적으로 늘어난다.
- 상품 하나의 가격이 변경되면, 해당 상품이 포함**될 수 있는** 모든 목록 캐시를 무효화해야 함
- 키 패턴 기반 일괄 삭제, TTL 기준 삭제, Versioning Key, Event-driven Invalidation 등 어떤 식으로 캐시 무효화를 하는지?

**핵심을 한 줄로**: 박수환 P0-3과 같은 고민. **목록 캐시의 무효화를 실무에서 어떻게 하냐?**

**Claude 답변**:

```
방법 1: 패턴 삭제 — KEYS product:list:*
→ KEYS 명령은 O(n)으로 Redis 전체를 스캔하면서 블로킹함
→ ⚠️ 프로덕션에서 절대 쓰면 안 됨 (수십만 키가 있으면 Redis가 수 초간 멈춤)
→ 대안: SCAN 명령 (논블로킹, 커서 기반으로 점진적 탐색, 하지만 느림)

방법 2: TTL에만 의존 — ✅ 실무에서 가장 많이 쓰는 방식
→ 가장 단순. "5분 동안 옛날 데이터가 보여도 괜찮은가?" → 목록은 대부분 괜찮음
→ 좋아요가 501에서 502로 바뀌어도 사용자는 인지하지 못함

방법 3: 캐시 키에 버전 넣기 (Versioning Key)
→ product:list:v42:brand=1:sort=LATEST:page=0
→ 상품 변경 시 버전을 43으로 올림 (Redis에 버전 카운터 저장)
→ v42 키는 TTL로 자연 만료, v43 키는 새로 생성
→ 깔끔하지만 버전 관리를 위한 별도 카운터 필요

방법 4: Event-driven Invalidation
→ 상품 변경 이벤트(Kafka, ApplicationEvent 등) 발행 → 이벤트 소비자가 관련 캐시 무효화
→ 생산자와 소비자가 분리되어 유연하지만, 이벤트 유실·지연 시 정합성 문제
→ MSA 환경에서 서비스 간 캐시 무효화에 주로 사용
```

**결론**: 대부분 방법 2(TTL 의존). 목록 데이터는 "최신 상태가 아니어도 사용자가 인지하기 어려움". Versioning Key는 키 폭발을 우회하는 깔끔한 방법이지만 버전 카운터 관리 부담이 있고, Event-driven은 MSA 규모에서 적합.

**멘토님 답변**:

- 캐시 무효화 시점과 방법에 따라 **장애 발생 가능성이 존재**
- 실무에서 캐시 무효화 로직에 대한 **버그가 많아** 신중한 설계가 필요 — "캐시 관련 장애의 70%는 무효화 로직 버그"라는 말이 있을 정도
- **크리티컬한 값은 캐시 무효화를 하지 않고, 무효화 없이 유지**하는 전략을 선호 — 메모리 낭비를 감수하더라도 무효화로 인한 데이터 불일치 위험을 줄이는 것이 더 중요
- 로컬 캐시를 사용해 **백그라운드에서 원자적으로 캐시 값을 교체**하는 방식도 활용

> **원자적 교체**: "삭제 → 빈 상태 → 새 값 저장" 대신 "옛날 값 → 새 값"으로 한 번에 바꾸는 것.
> 삭제 후 저장 사이에 다른 요청이 빈 캐시를 보고 DB를 치는 문제(Stampede)를 방지할 수 있다.
> 로컬 캐시에서는 ConcurrentHashMap의 `put()`이 원자적이라 가능하다.

### P1-3. 안유진: "Cache Stampede 방지"

**질문 해석**:
인기 상품의 상세 캐시 TTL이 만료되는 순간, 동시에 수백 개의 요청이 DB로 몰리는 상황(Cache Stampede / Thundering Herd).
- 이건 4주차에서 다뤘던 동시성 문제와 같은 구조
- 분산 락, TTL Jitter, Refresh-Ahead 중 실무에서 어떤 조합을 쓰는지?

**핵심을 한 줄로**: 캐시 TTL 만료 시 **1000명이 동시에 DB를 치는 것을 어떻게 막냐?**

```
t=0  인기 상품 캐시 TTL 만료
t=0  요청 1000개 동시 도착
     → 1000개 모두 캐시 miss
     → 1000개 모두 DB SELECT
     → DB에 갑자기 1000개 쿼리 폭탄 💥
     → 1000개 모두 같은 결과를 캐시에 저장 (999번 낭비)
```

**Claude 답변**:

| 방법 | 원리 | 장점 | 단점 |
|------|------|------|------|
| **분산 락** | 첫 번째 요청만 DB 조회, 나머지는 대기 후 캐시에서 읽음. Redis SETNX로 "이 키를 내가 갱신 중" 표시 | DB 부하 최소 (1건만 조회) | 대기 시간 발생, 락 관리 복잡, 락 건 요청이 실패하면? |
| **TTL Jitter** | TTL = 10분 ± 랜덤 2분 (8~12분). 같은 시점에 대량 만료 방지 | 구현 매우 간단 (TTL에 랜덤값 한 줄 추가) | stampede를 줄일 뿐 완전히 막지는 못함 |
| **Refresh-Ahead** | TTL 10분 중 8분째에 백그라운드로 미리 갱신. 만료 전에 새 값이 들어옴 | 사용자는 항상 캐시 hit, 응답 지연 없음 | 구현 복잡 (스케줄러 or 접근 시 남은 TTL 체크) |

**실무에서의 조합**:
- **기본 (모든 캐시에)**: TTL Jitter — 비용 거의 0, 한 줄 추가면 됨
- **핫 키에 추가**: 분산 락 — 인기 상품 TOP 100 같은 데만 선택적 적용
- **대규모 서비스**: Refresh-Ahead — 넷플릭스, 쿠팡 급에서 사용. 일반적인 서비스에서는 오버엔지니어링

**멘토님 답변**:

- **캐시 키 삭제 시 몰림 현상**에 주의 필요 — 이것이 바로 Cache Stampede
- 업데이트 시 캐시 키를 삭제하고 다음 조회 시 DB에서 다시 채우는 방식(라이크 파사드 패턴)이 가장 많이 사용되지만, 인기 상품에서는 삭제 직후 몰림이 발생할 수 있음

> **라이크 파사드 패턴**: 여기서 "라이크"는 좋아요(like)가 아니라 Cache-Aside와 유사한(like) 패턴이라는 뜻.
> "데이터 변경 시 캐시 삭제 → 다음 조회에서 DB로부터 다시 채움"이라는
> Cache-Aside의 무효화 전략을 의미한다. 가장 단순하고 널리 쓰이는 방식.

### P1-4. 안유진: "Read Replica vs Cache — 어떤 것을 먼저 도입하는가"

**질문 해석**:
읽기 부하를 분산하는 두 가지 방법:
1. DB Read Replica: 읽기 쿼리를 복제 DB로 분산
2. Redis Cache: DB 자체를 안 침
현재 프로젝트에 Redis가 이미 있으므로 둘 다 인프라적으로 가능한데, 어떤 것을 먼저 검토하는지?

**핵심을 한 줄로**: 읽기 성능 문제가 생겼을 때, **DB를 복제할 것인가 vs 결과를 캐시할 것인가?**

```
Read Replica:
→ DB 자체를 복제 → 쿼리는 여전히 실행됨, 서버만 분산
→ 어떤 종류의 쿼리든 효과적 (복잡한 JOIN, 집계도 OK)
→ 복제 지연(replication lag) 수백 ms 이내
→ 코드 변경 거의 없음 (DataSource 라우팅만 추가)

Cache:
→ 쿼리 결과를 저장 → 쿼리 자체를 안 침
→ 같은 조건의 반복 조회에만 효과적
→ 응답 sub-ms (메모리 접근)
→ 코드 변경 필요 (캐시 저장/조회/무효화 로직)
```

**Claude 답변**:

| 판단 질문 | → Cache | → Read Replica |
|----------|---------|---------------|
| 같은 조건으로 반복 조회가 많은가? | Yes (상품 상세, 카테고리) | No (관리자 다양한 검색) |
| 쿼리 자체가 무거운가? (복잡한 JOIN) | Yes (매번 실행하기 부담) | No (단순 쿼리) |
| 데이터 실시간성이 중요한가? | No (TTL 허용 범위 내) | Yes (복제 지연 수백ms 이내) |
| 코드 변경을 최소화하고 싶은가? | No (캐시 로직 추가 필요) | Yes (라우팅만 추가) |

**보통 Read Replica를 먼저 도입한다.** 이유:
- 애플리케이션 코드 변경이 거의 없음 (Spring의 `@Transactional(readOnly = true)` → Replica로 라우팅)
- 모든 종류의 읽기 쿼리에 즉시 효과
- 캐시는 코드 변경 + 무효화 전략 + 직렬화 + 장애 대응이 필요

캐시는 **"특정 API의 응답 시간을 극적으로 줄여야 할 때"** 추가. 예: 메인 페이지 상품 목록은 초당 만 건 → Read Replica로도 부족 → 캐시로 DB 자체를 안 침.

**멘토님 답변**:

- **레플리카 DB와 Redis 캐시 조합**으로 수백만 MAU도 충분히 처리 가능
- 단, **리드 모디파이 패턴**(읽고 → 수정 → 저장)에서 읽기를 레플리카로 하면 **데이터 꼬임 장애** 발생 가능 → 수정이 따라오는 읽기는 반드시 마스터 DB를 읽어야 함

```
✅ 단순 조회 (상품 목록, 상세 페이지): 레플리카에서 읽기 OK
❌ 수정이 따라오는 읽기 (재고 확인 → 차감, 잔액 조회 → 출금): 반드시 마스터에서 읽기
```

- 상세 페이지는 **실시간성을 높게** 유지하고, 전시 페이지(목록)는 **다소 지연을 허용** — 같은 캐시라도 페이지 성격에 따라 TTL을 다르게 설정
- 가격 등 크리티컬 데이터는 **실시간 계산이 필요해 별도 프라이싱 팀**에서 처리하는 경우도 있음

### P1-5. 김철중: "인덱스 생성/수정 기준"

**질문 해석**:
인덱스가 많아지면 쓰기 성능이 떨어진다고 들었는데, 실무에서 인덱스를 생성하거나 수정할 때 어떤 기준을 가지고 하는지?

**핵심을 한 줄로**: 안유진 P0-5와 연결. **인덱스를 추가/삭제하는 실무적 의사결정 프로세스**가 뭐냐?

**Claude 답변**:

실무에서의 인덱스 의사결정 프로세스:

```
1. 슬로우 쿼리 로그에서 느린 쿼리 발견 (또는 모니터링에서 응답 지연 감지)
2. EXPLAIN으로 Full Scan인지 확인
3. 해당 쿼리의 WHERE, ORDER BY, JOIN 조건 분석
4. 기존 인덱스로 커버 가능한지 확인 (기존 인덱스에 컬럼 추가로 해결 가능한 경우도 많음)
5. 안 되면 인덱스 추가/수정 검토
```

**추가/수정 전 체크리스트**:
- ☐ 이 쿼리가 **얼마나 자주 실행**되나? (초당 1회 vs 초당 1000회 → 자주 실행될수록 인덱스 가치 높음)
- ☐ 이 테이블에 인덱스가 **이미 몇 개**인가? (5개 이상이면 추가에 신중)
- ☐ 이 테이블의 **쓰기 빈도**는? (쓰기 많으면 인덱스 유지 비용 ↑)
- ☐ 기존 인덱스를 **확장(컬럼 추가)**해서 해결 가능한가? (새 인덱스보다 기존 확장이 나음)
- ☐ 이 인덱스가 **다른 쿼리에도 도움**이 되는가? (하나의 인덱스가 여러 쿼리를 커버하면 이상적)

**멘토님 답변**:

- **온라인 인덱스 생성/삭제 기능**을 적극 활용 — MySQL, PostgreSQL 등은 온라인 인덱스 생성/삭제 기능을 제공하여 **다운타임 없이** 인덱스 작업이 가능

> **온라인 인덱스(Online DDL)**: 서비스를 중단하지 않고 인덱스를 추가/삭제하는 기능.
> 예전에는 `ALTER TABLE ADD INDEX`를 실행하면 테이블 전체에 락이 걸려서
> 그동안 INSERT/UPDATE가 블로킹됐다. MySQL 5.6+부터는 Online DDL로
> 인덱스 생성 중에도 읽기/쓰기가 가능하다. 다만 완전히 무영향은 아니고
> 디스크 I/O가 증가하므로 트래픽이 적은 시간대에 실행하는 것이 안전하다.

- 복합 인덱스를 적극적으로 사용하지 않는 편 — **레퍼런스 ID(FK)와 정렬 컬럼 위주**로 설계
- 필터 조건이 많거나 데이터가 많은 경우에는 인덱스 설계에 더 신중

### P1-6. 서태수: "Redis에 캐시 값을 저장할 때 JSON vs 바이너리 직렬화"

**질문 해석**:
회사에서 Redis 캐시에 GZIP이나 바이너리로 직렬화해서 넣는 걸 본 적이 있다.
- JSON: 디버깅 편하지만 용량 큼
- 바이너리: 용량 효율적이지만 DTO 변경 시 역직렬화 깨질 수 있음
- 트래픽 규모나 데이터 크기에 따라 기준이 달라질 것 같은데?

**핵심을 한 줄로**: 캐시 데이터를 **사람이 읽을 수 있게(JSON) vs 기계가 효율적으로 읽게(바이너리)** 저장하냐?

```
JSON:
  {"name":"나이키 에어맥스","price":159000,"likeCount":42}
  → 사람이 redis-cli에서 바로 읽을 수 있음
  → 필드명이 반복되어 용량 큼

바이너리 (Kryo, Protobuf, JDK Serialization):
  0xAB3F7C01...
  → 사람이 읽을 수 없음
  → 용량 작음 (이름 없이 값만)
  → DTO에 필드 추가/삭제 시 역직렬화가 깨질 수 있음 (특히 JDK 직렬화)

GZIP:
  → JSON이든 바이너리든 압축 가능
  → 네트워크 대역폭 절약, 하지만 압축/해제 CPU 비용 추가
```

**Claude 답변**:

| 기준 | JSON | 바이너리 |
|------|------|---------|
| 디버깅 | ✅ redis-cli에서 바로 확인 | ❌ 별도 도구 필요 |
| 용량 | 크다 (필드명 반복) | 작다 (값만 저장) |
| DTO 변경 내성 | ✅ 새 필드는 null, 삭제된 필드 무시 | ❌ 깨질 수 있음 (특히 JDK 직렬화) |
| 성능 | 직렬화/역직렬화 약간 느림 | 빠름 |

**실무 기준**:
- **대부분 JSON** — 디버깅 편의성이 압도적. 캐시 데이터가 수 KB 수준이면 용량 차이 의미 없음
- **바이너리 고려 시점** — 캐시 데이터가 수 MB 이상이거나, Redis 메모리 비용이 문제될 때
- **GZIP** — 내부 네트워크에서는 대역폭이 병목인 경우가 드물어서 보통 불필요

현재 프로젝트의 `RedisTemplate<String, String>` + ObjectMapper 조합이 **실무에서도 가장 일반적인 선택**. 이 조합이면 redis-cli에서 `GET product:detail:42` 치면 바로 JSON이 보여서 장애 대응 시 매우 유용하다.

**멘토님 답변**:

- **JSON 문자열 형태로 캐시하는 것이 일반적** — 바이너리 저장은 DB 부하가 커서 권장하지 않음
- 캐시 키 개수보다 **캐시 데이터 총량을 계산하는 습관**이 중요
- Redis에 저장하는 데이터 크기가 **1~2MB 이하**일 경우 압축 필요성 낮음
- 최근 **CPU 성능 향상**으로 압축/해제 속도가 빨라져서, **서비스 간 API 호출 시 메시지를 압축 전송**하는 사례가 증가

> **메시지 압축 전송**: 마이크로서비스 간 API 호출 시 요청/응답 바디를 GZIP 등으로 압축하는 것.
> 예: 서비스A → 서비스B로 상품 목록 100개를 JSON으로 보내면 50KB인데,
> GZIP 압축하면 5KB로 줄어들어 네트워크 대역폭을 90% 절약할 수 있다.
> HTTP 헤더에 `Content-Encoding: gzip`을 넣으면 프레임워크가 자동으로 처리해준다.
> 예전에는 압축/해제 CPU 비용이 부담이었지만, 요즘 서버 CPU는 충분히 빨라서 문제없다.

- 리소스 간 전송도 압축하여 네트워크 효율을 높이는 추세

### P2. 안유진: "OFFSET 기반 페이지네이션의 한계와 실무 사용 사례"

**질문 해석**:
현재 Slice 기반 페이지네이션(LIMIT + 1)을 사용하는데 내부적으로는 여전히 OFFSET을 사용한다.
- OFFSET이 커지면 DB가 대량의 행을 읽고 버리므로 느려짐
- 커서 기반(keyset pagination)은 `WHERE id < :lastId` 형태로 효율적
- 그런데 POPULAR 정렬(likeCount DESC, id DESC)에서 커서를 적용하려면 `WHERE (like_count, id) < (:lastLikeCount, :lastId)` 같은 튜플 비교가 필요
- 이것이 인덱스를 제대로 타는지 의문
- 커서 기반이 이론적으로 낫다는 건 알겠지만, 사용량이 많지 않은 경우 오프셋도 많이 쓴다고 들었다. 커버링 인덱스, 페이지 수 캐싱, Slice 도입 등 최적화 방법도 있는데, 실무에서는 어떤 기준으로 선택하는지 궁금하다.

**핵심을 한 줄로**: **OFFSET의 비효율은 알겠는데, 다중 컬럼 정렬에서 커서는 어떻게 쓰고, 실무에서는 어떻게 선택하냐?**

```
OFFSET의 문제:
SELECT * FROM products ORDER BY id DESC LIMIT 20 OFFSET 10000;
→ DB가 10,020건을 읽고 앞의 10,000건을 버림
→ 페이지가 뒤로 갈수록 버리는 양이 늘어남 → 느려짐

커서 기반:
SELECT * FROM products WHERE id < 5000 ORDER BY id DESC LIMIT 20;
→ 인덱스에서 id=5000 바로 이전부터 20건만 읽음 → 항상 일정한 속도

다중 컬럼 정렬에서의 커서 (좋아요순):
마지막으로 본 상품: likeCount=100, id=500
SELECT * FROM products
WHERE (like_count < 100) OR (like_count = 100 AND id < 500)
ORDER BY like_count DESC, id DESC LIMIT 20;
→ OR 조건이 인덱스를 비효율적으로 사용할 수 있음
```

**Claude 답변**:

| UI 유형 | 추천 방식 | 이유 |
|--------|----------|------|
| 무한 스크롤 (모바일 피드) | 커서 기반 | 뒤로 갈수록 느려지면 안 됨 |
| 페이지 번호 (쇼핑몰 1, 2, 3...) | OFFSET | 특정 페이지로 점프 필요. 사용자가 100페이지까지 안 감 |

**다중 컬럼 정렬 + 커서 해결법**:
- OR 조건 대신 **복합 score로 합성**: `like_count * 1_000_000 + id` → 단일 컬럼 커서로 변환
- 또는 MySQL 8.0+에서 `ROW()` 구문: `WHERE ROW(like_count, id) < ROW(100, 500)` (인덱스 효율은 EXPLAIN으로 확인 필요)
- 실무에서도 이 부분은 까다로워서, 좋아요순 같은 **변동이 잦은 정렬은 OFFSET + 적당한 페이지 제한**(최대 50페이지)으로 처리하는 경우가 많음

**실무에서의 현실적 조합**:

```
관리자 페이지 (어드민):
→ OFFSET + COUNT → 페이지 번호 UI 필수, 트래픽 적어서 문제없음

대고객 목록 (상품 목록, 검색 결과):
→ Slice(LIMIT + 1) → "더보기" 버튼, COUNT 쿼리 제거
→ 페이지 수가 필요하면 COUNT 결과를 캐시 (5분 TTL)

피드/타임라인 (SNS, 댓글):
→ 커서 기반 → 무한 스크롤, 실시간 데이터 추가에 강함

OFFSET 최적화 팁:
→ 커버링 인덱스: SELECT id FROM products ORDER BY ... LIMIT 20 OFFSET 10000
   → 서브쿼리로 id만 빠르게 뽑고, 본 테이블에 JOIN
→ 페이지 제한: 최대 100페이지까지만 허용 (구글 검색도 이렇게 함)
```

**멘토님 답변**:

- **오프셋 기반 페이지네이션은 페이지가 뒤로 갈수록 성능 저하**가 발생 — 이건 이론대로
- 하지만 **커서 기반 페이지네이션은 UX 상 한계**가 있어서 (특정 페이지로 점프 불가), **실제 서비스에서는 오프셋 방식을 많이 사용**
- **슬라이스 기반 페이지네이션** 등 다양한 변형 기법이 존재

> **슬라이스 기반 페이지네이션**: `LIMIT 21`처럼 요청한 것보다 1개 더 조회해서,
> 21번째가 있으면 "다음 페이지 있음", 없으면 "마지막 페이지"로 판단하는 방식.
> `COUNT(*)`라는 무거운 쿼리를 날리지 않아도 "더보기" 버튼을 구현할 수 있다.
> Spring Data JPA의 `Slice<T>`가 이 방식을 지원한다.

핵심 정리:
```
"오프셋이 느린 건 사실이지만, 사용자가 1000페이지까지 가는 서비스는 거의 없다.
 대부분의 서비스에서 100페이지 제한 + 오프셋이면 충분하다."
```

## 캐시 핵심 개념 정리

### 캐시의 3가지 구성요소

| 구성요소 | 핵심 질문 | 설명 |
|---------|----------|------|
| **삽입** | 언제 넣을까? | Cache-Aside: 조회 시 없으면 DB에서 가져와 저장 (가장 일반적) |
| **TTL** | 얼마나 둘까? | 짧으면 정합성↑ 성능↓, 길면 정합성↓ 성능↑ |
| **Evict** | 언제 강제로 뺄까? | 데이터 변경 시 TTL 전에 강제 삭제. 단건은 쉽고 목록은 어려움 |

- TTL은 보험, Evict는 능동적 대응. 둘 다 있어야 안전

### LIKE '%keyword%' Full Scan 해결책

| | Full-Text Index | Elasticsearch |
|--|----------------|---------------|
| 본질 | MySQL 기능 확장 (역인덱스) | 별도 검색 시스템 |
| 도입 비용 | 낮음 (SQL만 추가) | 높음 (서버 + 동기화) |
| 검색 품질 | 기본적인 키워드 매칭 | 형태소 분석, 유사어, 랭킹 |
| 적합한 상황 | 소~중규모, 단순 검색 | 대규모, 검색이 핵심 기능 |

### B-Tree 인덱스

- "균형 잡힌 트리". 데이터를 정렬 상태로 유지하며 O(log n) 탐색 보장
- 10만건이어도 3~4번 비교면 찾음 (Full Scan이면 최악 10만 번)
- 복합 인덱스 `(brand_id, price)`: brand_id로 범위를 좁히고, price가 이미 정렬되어 있으니 filesort 불필요
