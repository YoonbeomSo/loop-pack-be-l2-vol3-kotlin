# [랭킹] 조회수 조작을 막는 랭킹 시스템 설계

> 봇이 10만 번 조회해도 정상 유저 50명보다 점수가 낮은 구조를 만들 수 있을까?

## TL;DR

- 랭킹 시스템에서 조회수는 가장 조작하기 쉬운 시그널이다
- Layer 1(userId/IP 중복 제거) + Layer 2(Trust Score 기반 점수 차등)으로 방어
- k6 테스트 결과, 봇 100회 조회가 정상 유저 50명의 1.4% 수준으로 억제됨

---

## 랭킹 시스템의 약한 고리 — 조회수

이번 주차에 Redis ZSET 기반 실시간 랭킹 시스템을 구현했습니다. 점수 공식은 이렇습니다.

```
Score = view × 0.1 + like × 0.2 + order금액 × 0.6
```

좋아요는 로그인이 필요하고, 주문은 결제가 필요합니다. 조작하려면 비용이 큽니다.

그런데 조회는? GET 요청 하나면 됩니다. 인증도 불필요합니다.

봇이 특정 상품을 1만 번 조회하면 `10,000 × 0.1 = 1,000점`. 정상적으로 좋아요 5,000건 받은 상품(1,000점)과 동급이 됩니다.

"조회수가 랭킹에 들어가는 한, 이건 반드시 막아야 하는 거 아닌가?"

---

## 빅테크는 어떻게 하고 있을까?

YouTube를 조사해봤습니다. YouTube는 3단계 방어를 씁니다.

- **Layer 1 (기본 필터)**: 같은 IP 반복 조회 감지, 30초 미만 시청 미반영
- **Layer 2 (패턴 인식)**: "수백 개 계정이 정확히 30초만 시청 후 이탈" 같은 봇 패턴 탐지
- **Layer 3 (머신러닝)**: ML 모델이 96% 이상의 인공 트래픽 식별

Layer 1은 우리도 할 수 있습니다. Layer 3은 데이터 사이언스 영역이고요.

흥미로운 건 **Layer 2의 접근법**이었습니다. 차단이 아니라 "행동 분석"입니다.

> 멘토님: "시스템 설계 면접에서는 단순 계산식보다는 대용량 트래픽 처리, 데이터 파이프라인 구성, 실시간 데이터 서빙 방법에 집중합니다."

## 첫 번째 시도 — 차단 방식의 한계

처음에는 단순하게 생각했습니다.

"같은 사람이 같은 상품을 여러 번 보면 1회만 반영하자."

### 상품 단위 감쇠를 검토했지만...

IP를 바꿔가며 조회하는 봇을 막으려면 상품 자체에 cap을 걸어야 합니다.

```
상품101의 시간당 조회:
  1~500건:    100% 반영
  501~1000건: 50% 반영
  2001건~:    0%
```

그런데 블랙프라이데이 세일로 진짜 5,000명이 몰리면? 정상 트래픽도 감쇠됩니다.

서버 입장에서 "진짜 인기"와 "봇 공격"을 구분할 수 없습니다. 두 경우 모두 "한 상품에 조회가 몰린다"는 패턴은 동일하니까요.

### 검토하고 버린 전략들

| 전략 | 왜 버렸는가 |
|------|-----------|
| 상품 단위 감쇠 | 이벤트로 진짜 인기 몰릴 때도 감쇠됨 |
| User-Agent 필터 | 위조가 너무 쉬움 (문자열 하나 바꾸면 끝) |
| 조회 속도 감지 | Layer 1에서 하루 1회로 이미 잡고 있어서 추가 효과 미미 |
| 후속 행동 기반 | 구현 복잡도 높고 실시간 반영 어려움 |

모든 전략이 **"진짜 트래픽을 해칠 수 있다"**는 공통 문제가 있었습니다.

---

## 발상의 전환 — 차단이 아니라 신뢰도

여기서 접근을 바꿨습니다.

```
기존 사고: 정상이면 반영, 비정상이면 차단 (이진적)
새로운 사고: 얼마나 신뢰할 수 있는 조회인가? (연속적)
```

차단하지 않되, **신뢰도에 따라 반영되는 점수가 달라지는 구조**입니다.

정상 로그인 유저는 풀 점수, 의심스러운 트래픽은 낮은 점수, 봇은 거의 0점.

이러면 이벤트로 정상 트래픽이 몰려도 로그인 유저들이니 풀 점수가 반영됩니다. 진짜 트래픽을 해치지 않습니다.

---

## 구현: 2계층 방어

### Layer 1: userId/IP 기반 일간 중복 제거

같은 사람이 같은 상품을 하루에 여러 번 조회해도 1회만 반영합니다.

**판단 우선순위**: userId가 있으면 userId로, 없으면 IP로 판단합니다.

```
로그인 유저A가 회사에서 조회 → key: dedup:20260410:101:user:A → 없음 → 반영
로그인 유저A가 집에서 재조회  → key: dedup:20260410:101:user:A → 있음 → skip
비로그인 회사에서 조회        → key: dedup:20260410:101:ip:1.1.1.1 → 없음 → 반영
비로그인 같은 IP 재조회       → key: dedup:20260410:101:ip:1.1.1.1 → 있음 → skip
```

같은 IP여도 로그인 유저끼리는 각각 반영됩니다. 회사 와이파이에서 직원 10명이 보면 10명 다 반영.

### Layer 2: Trust Score — 5개 시그널 기반 점수 차등

Layer 1을 통과한 조회에 대해 **신뢰도를 0~1.0으로 계산**합니다.

| 시그널 | 정상 | 의심 | 점수 | 왜 이 점수인가 |
|--------|------|------|------|--------------|
| 로그인 여부 | 로그인 | 비로그인 | 0.3 vs 0.05 | 아래 설명 |
| User-Agent 존재 | 있음 | 없음 | 0.1 vs 0 | 아래 설명 |
| Referer 존재 | 있음 | 없음 | 0.1 vs 0 | 아래 설명 |
| 분당 요청 수 | 1~3회 | 10회 이상 | 0.3 vs 0 | 아래 설명 |
| 10분 내 다른 상품 조회 | 3개 이상 | 1개만 반복 | 0.2 vs 0 | 아래 설명 |

#### 각 시그널에 이 가중치를 준 이유

**로그인 여부 (0.3 vs 0.05)** — 가장 큰 배점. 로그인 계정은 회원가입이 필요해서 **생성 비용**이 있습니다. 봇이 조회수를 조작하려면 비로그인은 GET 요청만 보내면 되지만, 로그인은 계정을 만들어야 하니까 대량 생성이 어렵고 추적도 가능합니다. 비로그인에 0이 아닌 0.05를 준 이유는, 처음 방문한 정상 유저가 로그인 없이 상품을 둘러보는 건 자연스러운 행동이기 때문입니다. 완전히 무시하면 정상 유저를 해치게 됩니다.

**분당 요청 수 (0.3 vs 0)** — 로그인과 동일한 배점. 사람은 1분에 상품을 1~3개 정도 보지만, 봇은 수십 건을 보냅니다. 분당 10회 이상이면 사람이 아닐 가능성이 높아서 0점을 줬습니다.

**10분 내 상품 다양성 (0.2)** — 정상 유저는 여러 상품을 탐색합니다. "에어맥스 보고, 울트라부스트 보고, 운동화 비교하고..." 반면 봇은 특정 상품 하나만 반복 조회합니다. 3개 이상 다양한 상품을 본 유저는 정상일 가능성이 높습니다.

**UA/Referer (각 0.1)** — 보조 시그널. 브라우저에서 접속하면 자동으로 붙는 헤더인데, 단순 스크립트 봇은 이걸 안 보냅니다. 다만 위조가 쉬워서 배점은 낮게 잡았습니다.

#### 합산 예시

```
정상 로그인 유저:
  로그인(0.3) + UA(0.1) + Referer(0.1) + 분당 2회(0.3) + 상품 5개 탐색(0.2) = 1.0

비로그인 정상 유저:
  비로그인(0.05) + UA(0.1) + Referer(0.1) + 분당 2회(0.3) + 상품 3개 탐색(0.2) = 0.75

봇 (UA 없음, 단일 상품 반복):
  비로그인(0.05) + UA 없음(0) + Referer 없음(0) + 분당 15회(0) + 상품 1개(0) = 0.05
```

**최종 점수 = 기본 조회 점수(0.1) x Trust Score**

정상 로그인 유저: `0.1 × 1.0 = 0.1점`
비로그인 정상 유저: `0.1 × 0.75 = 0.075점`
의심 봇: `0.1 × 0.05 = 0.005점`

같은 "1회 조회"인데 정상과 봇 사이에 **20배 차이**가 납니다.

## 왜 이 조합이 진짜 트래픽을 해치지 않는가

| 시나리오 | Layer 1 | Layer 2 | 결과 |
|---------|---------|---------|------|
| 정상 유저 100명 | 100명 모두 통과 | x1.0 (로그인+UA+Referer) | 높은 점수 |
| 봇 1대 100회 | 1회만 통과 | x0.05 | 매우 낮은 점수 |
| 봇 IP 100개 | 100개 통과 | x0.05 (비로그인+UA없음) | 낮은 점수 |
| 이벤트 유저 1000명 | 1000명 통과 | x1.0 | 매우 높은 점수 |

**봇은 여러 시그널에서 동시에 낮은 점수를 받습니다.** UA를 위조해도 로그인이 없으면 0.3 → 0.05. 하나만 위조해선 다른 시그널에서 걸립니다.

## k6로 검증: 봇 vs 정상 유저

말로만 하면 안 되니까 k6 부하 테스트로 실제 검증했습니다.

### 소규모 테스트 (1x)

| 시나리오 | VU | 반복 | 특징 |
|---------|-----|------|------|
| 정상 유저 | 5명 | 2회 | 로그인 + UA + Referer |
| 단일 IP 봇 | 1대 | 10회 | 비로그인, 50ms 간격 |
| UA없는 봇 | 5개 | 1회 | 비로그인, UA/Referer 없음 |

```
결과:
  1위: 상품1 (score: 0.4000) ← 정상 유저
  2위: 상품3 (score: 0.0550) ← UA없는 봇
  3위: 상품2 (score: 0.0450) ← 단일 IP 봇
```

**봇이 10회 조회해도 정상 유저 5명의 11% 수준.**

### 10배 스케일 테스트 (10x)

| 시나리오 | VU | 반복 |
|---------|-----|------|
| 정상 유저 | 50명 | 2회 |
| 단일 IP 봇 | 1대 | 100회 |
| UA없는 봇 | 50개 | 1회 |

```
결과:
  1위: 상품1 (score: 4.0000) ← 정상 유저 50명
  2위: 상품2 (score: 0.0550) ← 단일 IP 봇 100회
  3위: 상품3 (score: 0.0450) ← UA없는 봇 50개
```

| 상품 | 시나리오 | 요청 수 | 점수 | 정상 대비 |
|------|---------|--------|------|----------|
| 상품1 | 정상 유저 50명 | 100회 | 4.0000 | 100% |
| 상품2 | 단일 IP 봇 | 100회 | 0.0550 | 1.4% |
| 상품3 | UA없는 봇 50개 | 50회 | 0.0450 | 1.1% |

**봇이 100회 조회해도 정상 유저 50명의 1.4%.**

핵심: 봇 점수는 Layer 1에서 1회로 제한되어 **고정**, 정상 유저 점수는 인원에 비례해 **선형 증가**. 유저가 늘어날수록 봇의 영향력은 더 작아집니다.

## 완벽하지 않다는 걸 안다

이 방어가 완벽한 건 아닙니다.

- **IP 우회 + 로그인 계정 대량 생성**: 봇이 수천 개의 가짜 계정을 만들면 Layer 1도 Layer 2도 뚫립니다
- **계정 연령 시그널**: 신규 계정은 Trust Score를 낮추려 했지만, 이번 구현에서는 유저 서비스 조회 비용 때문에 제외
- **ML 없는 한계**: YouTube가 96% 탐지율을 달성하는 건 ML 때문이고, 규칙 기반으로는 한계가 있습니다

> 멘토님: "대규모 기업에서는 데이터 사이언티스트들이 복잡한 모델과 계산식을 개발하여 고도화된 스코어링 로직을 운영합니다."

하지만 **Layer 1(중복 제거)은 빅테크에서도 기본으로 까는 정석**이고, Trust Score는 ML 없이 "행동 분석"을 규칙 기반으로 근사한 시도입니다. "완벽한 차단"이 아니라 "합리적인 수준의 방어"가 목표였고, k6 결과가 그걸 증명했다고 생각합니다.

---

## 마무리

> 어뷰징 방지는 "완벽한 차단"이 목표가 아니라 "합리적인 수준의 방어"가 목표다.
> 진짜 트래픽을 해치지 않으면서 봇의 영향력을 최소화하는 것 — 그 균형을 찾는 과정이 설계의 핵심이었다.
