# 8주차 대화 로그

## 2026-03-30: 대기열 시스템 전체 흐름 학습 — Rate Limiting vs Queuing, 왜 대기열인가

### 고민한 부분
- 블랙프라이데이 트래픽 폭증 시 Rate Limiting(거부)과 Queuing(대기) 중 어떤 전략이 맞는가?
- R7 Kafka 버퍼링과 R8 대기열의 차이는 무엇인가?
- Redis Sorted Set이 대기열에 적합한 이유는 무엇인가?

### 선택지
1. **Rate Limiting** — 초과 요청을 429로 거부. 단순하지만 유저가 새로고침 → 재시도 폭풍 악순환.
2. **Queuing (대기열)** — 초과 요청을 보관하고 순서대로 처리. 유저가 기다릴 의사가 있는 상황에 적합.

### 선택한 답
- 대기열 방식 선택
- 이유: 블랙프라이데이는 유저가 기다려서라도 사고 싶은 상황. "나중에 다시 오세요"는 이탈과 재시도 폭풍만 유발. 줄을 세우고 순번을 보여주는 게 유저 경험과 시스템 보호 모두에 적합.

### 느낀 점
- Kafka 버퍼링(R7)은 fire & forget이었는데, 주문은 유저가 화면 앞에서 기다리는 상황이라 실시간 피드백이 필수. 같은 "줄 세우기"라도 유저 경험에 따라 설계가 완전히 달라진다는 걸 느꼈다.

## 2026-03-30: 스케줄러 배치 발급과 Polling 주기의 관계 — 동시 호출이 몰리지 않는 이유

### 고민한 부분
- 스케줄러가 100ms마다 18명씩 토큰을 발급하는데, Polling은 2000ms마다 조회한다. 그러면 2초 동안 20×18=360명의 토큰이 쌓이고, 한꺼번에 주문 API에 몰리는 거 아닌가?

### 선택지
1. **몰린다** — 360명이 Polling 시점에 동시에 토큰을 발견하고 일제히 주문 호출.
2. **몰리지 않는다** — 유저마다 Polling 시작 시점이 다르므로 토큰 발견 타이밍이 자연스럽게 분산된다.

### 선택한 답
- 2번. 몰리지 않는다.
- 이유: 유저마다 대기열 진입 시각이 다르기 때문에 Polling 주기도 제각각이다. 유저A는 0.3초에, 유저B는 1.2초에 토큰을 발견하게 되어 주문 API 호출이 자연스럽게 분산된다. 2초 Polling이 오히려 자연스러운 Jitter 역할을 하는 셈.

### 느낀 점
- 처음엔 "2초 동안 쌓이면 한꺼번에 터지는 거 아닌가?" 싶었는데, 유저별 Polling 타이밍이 다르다는 걸 깨달으니 납득됐다. 오히려 SSE로 토큰 발급 즉시 Push하면 동시 호출이 더 몰릴 수 있다는 게 재밌었다. 평탄화는 토큰 발급 단계(100ms 배치)와 주문 호출 단계(Polling 분산) 두 겹으로 이뤄진다.

## 2026-03-30: 계획 리뷰 — 놓친 포인트 4가지

### 고민한 부분
- 작성한 구현 계획을 리뷰하면서, 빠진 고려사항이 없는지 점검했다.

### 1. 토큰 삭제 시 ApplicationEvent 활용

- 원래 계획: `validateAndConsumeToken()`에서 토큰을 직접 삭제
- 개선: 주문 완료 후 `EntryTokenConsumedEvent` 발행 → 핸들러에서 토큰 삭제 + 모니터링 지표 수집
- 이유: R7에서 구축한 이벤트 패턴과 일관성 유지. 토큰 삭제 실패가 주문 실패로 이어지지 않도록 핵심 경로에서 분리. Token Conversion Rate 같은 운영 지표 수집 기반도 마련됨.
- 느낀 점: 단순히 "삭제하면 끝"이 아니라, 삭제라는 행위 자체가 비즈니스 이벤트(토큰 소비)라는 관점이 새로웠다.

### 2. 예상 대기시간 산출 근거

- 원래 계획: `position / 175` 한 줄뿐이었음
- 문제: 175라는 숫자가 이론값(DB 풀 50 / 0.2s = 250 × 70%)인데, 실제 주문 처리 시간은 재고 락, 결제 연동, 쿠폰 적용에 따라 달라질 수 있음
- 개선: "이론값 → k6 실측 → 보정" 흐름을 계획에 명시
- 느낀 점: 숫자 하나를 내놓더라도 "이건 가정이다, 실측 후 바뀔 수 있다"를 명시하는 게 엔지니어링 문서의 신뢰를 높인다.

### 3. k6 부하 테스트 — 빌드 파이프라인 밖에서

- 고민: 통합 테스트로 트래픽 테스트를 넣으면 빌드가 느려지지 않을까?
- 답: k6는 Gradle 빌드 밖에서 실행. bootRun으로 앱 띄우고 k6 스크립트를 별도 실행하므로 빌드 시간에 영향 없음.
- 계획에 Step 6으로 k6 부하 테스트 단계 추가함.
- 느낀 점: 성능 테스트와 기능 테스트는 실행 환경 자체가 다르다는 걸 인식하게 됐다.

### 4. 블로그 작성 포인트

- 단순 "이걸 했다" 나열이 아니라, 특정 포인트에 deep dive하는 글
- 배경지식을 활용한 자료조사 과정 자체를 보여주는 것
- SRP 관점에서 대기열/토큰/스케줄러의 책임 분리를 분석해보는 것
- 느낀 점: 코드를 짜는 것과 "왜 이렇게 짰는지"를 글로 설명하는 건 완전히 다른 능력이다. 과정을 기록하는 습관이 포트폴리오가 된다.

## 2026-03-30: Token Expiry Rate — TTL 5분의 근거를 어떻게 검증할 것인가

### 고민한 부분
- TTL로 토큰이 자동 만료되는데, Redis TTL 만료는 이벤트를 발생시키지 않는다. "누가 만료됐는지"를 직접 알 수 없는데, 만료율은 어떻게 측정하지?
- TTL 5분이 적절한지를 어떤 지표로 검증할 수 있는가?

### 선택지
1. **Redis Keyspace Notification** — TTL 만료 시 이벤트를 수신. 정확하지만 Redis 설정 변경이 필요하고 복잡도 증가.
2. **산술 계산** — 발급 카운터와 소비 카운터의 차이로 간접 측정. 단순하고 별도 인프라 불필요.

### 선택한 답
- 2번. 산술 계산.
- `Token Expiry Rate = (발급 수 - 소비 수) / 발급 수`
- QueueService에 발급/소비 카운터를 두고, EntryTokenEventHandler에서 소비 시 카운트 증가.
- 이유: 이번 과제 범위에서는 정확한 실시간 만료 감지보다 "TTL이 적절한가?"를 판단할 수 있으면 충분. 산술 계산으로도 만료율 추세를 파악할 수 있다.

### 느낀 점
- "토큰이 만료됐다"는 사실은 Redis가 알아서 처리하지만, "만료율이 높다"는 비즈니스 판단은 우리가 직접 측정해야 한다는 걸 깨달았다. 통합 테스트에서 TTL을 짧게(1~2초) 설정해서 만료 시나리오를 재현하고, 만료율 계산이 정확한지 검증하는 테스트를 계획에 추가했다.

## 2026-03-30: Jitter A/B 비교와 Nice-to-Have 설계

### 고민한 부분
- Jitter를 넣었을 때와 안 넣었을 때 실제로 차이가 있는지 어떻게 증명할 수 있을까?
- Nice-to-Have(동적 Polling 주기, Jitter, Graceful Degradation)를 어떤 기준으로 적용할지

### 선택지
1. **감으로 적용** — "Jitter가 좋다고 하니까 넣자"
2. **k6로 A/B 비교 후 데이터 기반 판단** — 동일 부하에서 Jitter 유무에 따른 P99, 에러율, DB 커넥션 피크 비교

### 선택한 답
- 2번. k6 A/B 비교.
- Must-Have(Step 1~5) 완료 → k6 실측(Step 6) → 데이터 기반으로 Nice-to-Have 필요성 판단
- 블로그 소재로도 좋음: "Jitter를 넣었더니 P99가 X% 개선됐다" vs "이미 Polling 분산이 충분해서 차이가 없었다"

### Nice-to-Have 적용 기준 정리
- **Jitter**: k6에서 P99 응답시간이 유의미하게 차이날 때
- **동적 Polling 주기**: k6 Polling 부하 시나리오에서 순번 조회 API P99가 높아질 때
- **Graceful Degradation**: 구현 우선순위는 낮지만, 어떤 전략(전면 차단/우회/Fallback)을 쓸지 사전에 결정해두는 것이 핵심

### 느낀 점
- "좋다고 하니까 넣자"가 아니라 "데이터로 증명하고 넣자"가 엔지니어의 태도라는 걸 다시 느꼈다. Nice-to-Have를 계획에 미리 설계해두되, 실측 후 판단하는 흐름이 실무적이다.

## 2026-03-31: 스케줄러 원자성 문제 — ZPOPMIN 후 죽으면 유저가 유실된다

### 고민한 부분
- 스케줄러가 ZPOPMIN으로 유저를 대기열에서 꺼낸 직후, 토큰 발급(SET EX) 전에 죽으면 유저는 대기열에도 없고 토큰도 없는 상태가 된다.
- 이걸 어떻게 원자적으로 보장할 수 있는가?

### 선택지
1. **Lua 스크립트** — ZPOPMIN + SET EX를 하나의 원자적 연산으로 묶음. 단일 Redis에서 가장 확실.
2. **보상 로직** — 임시 Set(queue:processing)에 저장 후 토큰 발급. 실패한 유저는 보상 스케줄러가 대기열에 재삽입. Cluster 호환.
3. **2단계 분리** — ZPOPMIN 대신 ZRANGEBYSCORE로 조회만 하고, 토큰 발급 성공한 유저만 ZREM으로 삭제. SET NX로 중복 방지. Cluster 호환 + 유저 유실 없음.

### 선택한 답
- 우리 프로젝트는 단일 Redis(Master-Replica)이므로 **Lua 스크립트**가 가장 깔끔.
- 분산 환경(Redis Cluster)이라면 **2단계 분리**가 실무에서 가장 많이 쓰이는 방식. 보상 로직 없이도 유저 유실이 없고 구현이 단순하기 때문.

### 느낀 점
- "ZPOPMIN 한 줄이면 되지"라고 생각했는데, 그 한 줄 다음에 서버가 죽는 시나리오를 떠올리니까 완전히 달라졌다. 분산 시스템에서 "두 연산 사이에 뭐든 일어날 수 있다"는 사고방식이 중요하다는 걸 깨달았다. 단일 Redis vs Cluster에 따라 해법이 달라지는 것도 재밌었다.

## 2026-03-31: 단일 서버인데 Redis가 꼭 필요한가? — In-Memory vs Redis

### 고민한 부분
- 서버가 한 대인데 굳이 Redis를 써야 하는가? ConcurrentSkipListMap + ConcurrentHashMap으로 In-Memory 대기열을 만들면 안 되는가?

### 선택지
1. **In-Memory** — 외부 의존성 없이 단순. 하지만 서버 재시작 시 대기열 전부 소멸, 스케일아웃 불가, TTL/원자적 연산 직접 구현 필요.
2. **Redis** — 서버 재시작해도 대기열 유지, 스케일아웃 시 공유 가능, TTL/원자적 연산 내장.

### 선택한 답
- Redis.
- 이유: 대기열이 필요한 상황 자체가 트래픽 폭증(블랙프라이데이)이다. 그 순간에 핫픽스 배포나 장애로 서버가 재시작되면 In-Memory 대기열은 전부 소멸한다. 줄 서있던 1만 명이 증발하는 건 서비스 사고. Redis를 쓰는 이유는 성능이 아니라 **내구성(durability)과 확장 가능성**.

### 느낀 점
- "지금 단일이니까 In-Memory로 해도 되지 않나?"라는 생각이 들었지만, "대기열이 필요한 시점 = 가장 트래픽이 많은 시점 = 장애가 날 가능성이 가장 높은 시점"이라는 걸 깨닫고 납득됐다. 기술 선택의 이유를 "지금 되는가"가 아니라 "가장 중요한 순간에도 되는가"로 판단해야 한다.

## 2026-04-01: Lua 스크립트 어디까지 쓸 것인가 — 원자성 vs 관리 비용의 트레이드오프

### 고민한 부분
- 대기열 진입(addToQueue)에서도 Lua 스크립트를 써야 하는가? 다중 서버 환경에서 Redis 시간으로 score를 계산하고, 중복 체크 + ZADD + ZRANK를 원자적으로 묶으면 공정성과 정확성이 보장된다.
- 하지만 Lua를 쓸수록 관리 포인트가 늘어나지 않나?

### 선택지
1. **전부 Lua로** — addToQueue도 Lua로 묶어서 공정성 + 중복 방지 + 정확한 순번을 완벽히 보장
2. **토큰 발급만 Lua로** — addToQueue는 앱 코드로 유지. 순번 오차(1~2)는 "약 N번째"로 허용

### Lua의 단점
- Kotlin 코드 안에 Lua 문자열이 섞여서 가독성 저하
- Lua 로직은 단위 테스트 불가 (Redis 띄워야만 검증)
- 비즈니스 로직이 앱과 Redis 두 곳에 분산되어 관리 포인트 증가
- Lua 실행 중 Redis가 다른 명령을 못 받음 (블로킹)

### 선택한 답
- 2번. 토큰 발급만 Lua, 나머지는 앱 코드.
- 판단 기준: **"유저 유실은 사고, 순번 1 밀리는 건 오차"**
  - ZPOPMIN + SET EX (토큰 발급): 중간에 죽으면 유저가 유실됨 → **Lua 필수**
  - ZADD + ZRANK (대기열 진입): 순번이 1~2 밀려도 "약 N번째"로 표현하면 충분 → **Lua 불필요**
  - 중복 진입 방지: Sorted Set 특성 + 앱 레벨 체크로 충분 → **Lua 불필요**
  - Redis 시간 score: NTP 동기화 서버라면 clock skew는 수ms 수준 → **Lua 불필요**

### 느낀 점
- Lua가 원자성을 보장한다고 무조건 좋은 게 아니다. "이 연산이 원자적이지 않으면 무슨 일이 일어나는가?"를 먼저 따져보고, 그 결과가 치명적일 때만 Lua를 쓰는 게 맞다. 관리 비용과 원자성 보장 사이의 트레이드오프를 의식적으로 판단하는 연습이 됐다. 블로그 deep dive 소재로도 좋을 것 같다.

## 2026-04-01: Kafka vs Redis — 왜 대기열에 Kafka를 안 쓰는가

### 고민한 부분
- R7에서 Kafka로 선착순 쿠폰 버퍼링을 했는데, R8 대기열도 "줄 세우기"인데 왜 Kafka가 아닌 Redis인가?
- Kafka를 선택한 이유, ApplicationEvent → Kafka 전환 기준, 대기열에서 Redis를 선택한 근거를 정리하고 싶었다.

### 정리한 내용

**1) 왜 Kafka인가 (R7)**
- 로그 기반 → 소비 후에도 메시지 보존, 재소비 가능
- Consumer Group 독립성 → A가 느려도 B에 영향 없음
- 새 Consumer 추가 시 과거 이벤트부터 재처리 가능 (RabbitMQ는 불가)

**2) ApplicationEvent → Kafka 전환 기준**
- 같은 앱 안에서만 소비 → ApplicationEvent
- 다른 앱도 필요하거나 유실이 치명적 → Kafka
- "처음부터 Kafka로 안 가고, 문제가 생기면 고도화"하는 실무적 판단

**3) R8 대기열에 Kafka를 안 쓴 이유**
- Kafka는 "넣고 나면 내 위치를 모른다" → 순번 조회 불가능
- 대기열은 유저가 화면 앞에서 "지금 몇 번째야?"를 계속 확인하는 시나리오
- Redis Sorted Set은 ZRANK로 즉시 순번 조회, SET + TTL로 토큰 관리까지 가능
- Kafka는 비동기 파이프라인에 맞고, 대기열은 실시간 피드백에 맞음

**4) 전체 파이프라인에서의 역할 분리**
- 대기열(Redis) = 주문 API 앞단의 관문 (R8)
- Kafka = 주문 이후의 데이터 파이프라인 (R7)
- 둘은 양자택일이 아니라 각자의 위치에서 연결되는 구조

### 느낀 점
- "Kafka도 줄 세우기 아냐?"라는 질문에 처음엔 명확히 답하지 못했는데, 핵심 차이가 "내 위치를 알 수 있는가"라는 걸 깨달았다. 같은 "버퍼링"이라도 유저 경험에 따라 적합한 기술이 완전히 달라진다. 기술 선택은 기능이 아니라 시나리오에 맞춰야 한다.

## 2026-04-01: log.warn만으로 실패를 파악할 수 있는가 — 로깅 vs 모니터링

### 고민한 부분
- EntryTokenEventHandler에서 토큰 삭제 실패 시 `log.warn`만 남기는데, 개발자가 이걸 보고 버그를 파악할 수 있는가?

### 선택지
1. **log.warn만** — 로그 파일에 기록. 누군가 찾아봐야 알 수 있음.
2. **모니터링 지표 추가** — Micrometer Counter로 실패 횟수 집계 → Grafana 대시보드 → 임계치 초과 시 알림.

### 선택한 답
- 이번 과제에서는 log.warn 유지.
- 이유: 토큰 삭제 실패해도 TTL 5분 후 자동 만료라 치명적이지 않음. 모니터링 인프라(Grafana, 알림)는 과제 범위 밖.
- 단, "실무라면 여기에 모니터링을 붙여야 한다"는 인식은 블로그에서 언급할 포인트.

### 느낀 점
- log.warn은 "기록은 했다"일 뿐, "누군가 본다"는 보장이 없다. 실무에서는 로그 → 지표 수집 → 대시보드 → 알림까지 이어져야 운영 가능한 시스템이다. "지금은 과제 범위 밖이지만 부족하다는 걸 안다"와 "충분하다고 생각한다"는 면접에서 완전히 다른 답이 된다.

## 2026-04-02: 새로고침하면 순번이 뒤로 밀리는 이유 — userId 기반 vs 세션 기반

### 고민한 부분
- 실제 서비스에서는 새로고침하면 대기열 맨 뒤로 가는데, 우리 구현에서는 왜 순번이 유지되는가?

### 정리한 내용
- 실제 서비스(티켓팅, 한정판 구매)는 **비로그인 상태에서도 대기**해야 하므로 세션/쿠키 기반으로 유저를 식별한다. 새로고침하면 세션이 새로 발급되어 Redis 입장에서는 다른 유저로 인식 → 맨 뒤로 밀림.
- 우리 구현은 **로그인 기반**(X-Loopers-LoginId)이라 userId가 member. `addIfAbsent`로 같은 userId는 score 갱신 없이 기존 순번 유지.

### 느낀 점
- 같은 대기열 시스템이라도 유저 식별 방식(userId vs sessionId)에 따라 새로고침 동작이 완전히 달라진다. "왜 뒤로 밀리지?"라는 질문에 "세션이 바뀌니까"라고 답할 수 있으면 대기열의 동작 원리를 이해한 거다. 통합 테스트에서 같은 유저 재진입 시 순번 유지를 검증한 것도 이 맥락이었다.

## 2026-04-02: k6 시나리오 기반 부하 테스트 — 500 VU vs 1000 VU 비교 (블로그 핵심 소재)

### 고민한 부분
- 이전 테스트에서 TPS를 역추적하려 했으나, 이번 과제의 핵심은 "TPS가 높은 상황을 가정하고 대기열이 시스템을 보호하는지 검증"하는 것.
- TPS를 높게 설정하고 대기열의 동작을 관찰하는 방식으로 전환.

### 시나리오 구성
1. **블랙프라이데이 진입** — N명이 30초간 동시에 대기열 진입 + Polling
2. **전체 흐름** — 진입 → Polling → 토큰 대기 → 주문 (실제 유저 경험)
3. **스파이크** — 1초 만에 N명 폭증

### 500 VU vs 1000 VU 비교 결과

| 메트릭 | 500 VU | 1000 VU | 변화 |
|--------|--------|---------|------|
| 대기열 진입 avg | 1,989ms | 4,600ms | 2.3배 악화 |
| 대기열 진입 P95 | 3,586ms | 8,790ms | 2.5배 악화 |
| Polling P95 | 3,562ms | 8,820ms | 2.5배 악화 |
| **주문 P95** | **1,619ms** | **1,690ms** | **거의 동일** |
| **토큰 대기 avg** | **587ms** | **585ms** | **거의 동일** |
| 주문 성공 | 2,380건 (14.3/s) | 2,238건 (10.7/s) | 소폭 감소 |
| **주문 성공률** | **100%** | **100%** | **동일** |
| **HTTP 실패율** | **0%** | **0%** | **동일** |

### 핵심 발견 (블로그 포인트)

1. **대기열이 시스템을 보호하고 있다** — 1000명이 동시에 몰려도 에러율 0%, 주문 성공률 100%. 대기열 없이 1000명이 직접 주문 API를 호출했다면 DB 커넥션 고갈로 장애가 발생했을 것.

2. **병목은 대기열 진입/Polling이지 주문이 아니다** — 진입 P95가 8.8초까지 느려졌지만, 이건 Tomcat 스레드 200개가 1000명을 처리하느라 큐잉된 것. 주문 P95는 1.7초로 500 VU와 차이 없음.

3. **대기열의 핵심 가치 증명** — "진입은 느려지더라도, 주문 처리 자체는 안정적으로 보호된다." 이것이 Back-pressure의 본질. 유저는 진입 시 잠깐 기다리지만, 토큰을 받으면 안정적으로 주문할 수 있다.

4. **토큰 대기 시간이 VU 수에 무관하게 안정적** — avg 585ms. 스케줄러가 100ms마다 18명씩 일정하게 발급하기 때문. 대기열에 몇 명이 쌓여있든 토큰 발급 속도는 일정.

### 느낀 점
- 처음엔 "실제 TPS를 측정해서 배치 크기를 보정하자"는 접근이었는데, "TPS가 높은 상황을 가정하고 대기열이 보호하는지 검증하자"로 전환한 게 훨씬 의미 있었다. 이번 과제의 목적에 맞는 관점 전환.
- 500 → 1000으로 올렸을 때 진입은 느려지지만 주문은 안정적이라는 결과가 대기열의 존재 이유를 명확히 보여준다. 블로그에서 이 비교 테이블 하나만으로도 "왜 대기열을 쓰는가"를 설명할 수 있다.

### 부하 테스트 진행 과정 요약 (블로그 스토리 라인)

**1차 (100 VU) — "측정하자"**
- 시나리오: 대기열 진입 100 VU, Polling 200 VU, 주문 50 VU 순차 실행
- 문제: 스케줄러가 test 프로파일로 비활성화되어 토큰 발급 0건 → 주문 성공 0건
- 수정: local/test 프로파일 분리
- 재실행 결과: 주문 1,920건, 11.5 TPS. 대기열/Polling P95 80ms로 양호
- 발견: 이론(175 TPS)과 실측(11.5 TPS)의 15배 괴리. DB 커넥션 풀이 40인데도 낮은 이유는 VU가 적고 토큰 대기에 시간을 많이 쓰기 때문
- 접근 전환: "TPS를 역추적하지 말고, 높은 부하를 가정하고 대기열이 보호하는지 검증하자"

**2차 (500 VU) — "대기열이 보호하는가?"**
- 시나리오 재설계: 블랙프라이데이(500명 동시 진입) + 전체 흐름(100 VU) + 스파이크(500명 폭증)
- 결과: 대기열 진입 P95 3.6초, Polling P95 3.6초, 주문 P95 1.6초, 에러율 0%
- 발견: 진입/Polling은 느려지지만 주문은 안정적. 대기열이 보호하고 있음

**3차 (1000 VU) — "한계까지 밀어보자"**
- 500에서 1000으로 VU 2배 증가
- 결과: 진입 P95 8.8초(2.5배 악화), 주문 P95 1.7초(거의 동일), 에러율 0%
- 발견: 진입은 더 느려지지만 주문은 여전히 안정적. 토큰 대기도 avg 585ms로 변화 없음
