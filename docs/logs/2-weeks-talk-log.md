# 2주차 논의 기록

> 블로그 작성용 - 이번 주차에 어떤 고민을 했는지 기록

## 세션 1: 설계 문서 작성 세션

### 논의 1: 설계 문서 작성 순서

**질문**: 설계 문서는 시퀀스부터 작성해? 순서가 어떻게 돼?

**결론**: 추상화 수준이 높은 것 → 낮은 것 순서로 작성

```
요구사항 정의 → 유저 시나리오 → 시퀀스 → 클래스 → ERD
(What)                                              (How)
```

| 순서 | 문서 | 질문 |
|------|------|------|
| 1 | 요구사항 | 무엇을? |
| 2 | 유저 시나리오 | 누가 어떻게? |
| 3 | 시퀀스 | 어떤 순서로? |
| 4 | 클래스 | 어떤 구조로? |
| 5 | ERD | 어떻게 저장? |

---

### 논의 2: 이커머스 설계 전 결정해야 할 선택사항들

**질문**: 이커머스지만 자사몰인지 외부몰인지에 따라서도 설계가 달라질 수 있고, 내가 선택사항이 있어야 하지 않아?

**깨달음**: 요구사항이 모호하면 설계도 모호해진다. 설계 전에 전제 조건을 명확히 해야 함.

**결정이 필요했던 항목들**:

| 항목 | 선택지 | 최종 결정 |
|------|--------|----------|
| 비즈니스 모델 | 자사몰 vs 마켓플레이스 | **자사몰** |
| 재고 관리 | 단일 vs 창고별 vs 외부연동 | **단일 재고** |
| 주문/결제 흐름 | 즉시 결제 vs 분리 | **주문 즉시 결제** |
| 주문 종류 | 단일 상품 vs 장바구니 | **둘 다 지원** |
| 상품 구조 | 단일 vs 옵션 vs SKU | **옵션 상품 (복합 옵션)** |
| 삭제 정책 | Hard Delete vs Soft Delete | **Soft Delete** |

---

### 논의 3: 추가 요구사항 상세화

**질문**: 2주차 범위에 포함되는 것들의 상세 요구사항은?

**결정 사항들**:

#### 옵션 상품
- 복합 옵션 방식 (사이즈 + 색상 조합)
- 옵션별 가격 추가금, 재고 개별 관리

#### 장바구니
- 장바구니 API 필요 (조회/추가/수정/삭제/비우기)
- 유효기간 DB에서 관리 (만료일 저장)

#### 쿠폰
- 정액/정률 둘 다 지원
- 적용 범위: 전체 주문
- 중복 사용 불가 (주문당 1개)

#### 주문 취소/환불
- 취소 가능 시점: 주문수집 전까지만
- 환불 처리: 어드민 수동 처리
- 재고 복구: 취소 시 자동 복구

#### 배송
- 배송지 관리 (회원별 배송지 목록)
- 배송비 정책 (무료/고정/조건부 무료)

### 논의 4: 어드민 인증 API 누락

**질문**: 어드민 회원 관련 API가 없는 것 같아. `X-Loopers-Ldap` 헤더를 받으려면 관리자도 로그인해야 하는 거 아니야?

**깨달음**: 어드민 인증 관련 API가 누락되어 있었음

**선택지**:
| 방식 | 설명 |
|------|------|
| A. 자체 로그인 | 어드민 로그인 API → 토큰 발급 → 헤더에 전달 |
| B. 외부 LDAP 연동 | 외부 LDAP 서버 인증 → 헤더에 LDAP 정보 전달 |

**최종 결정**: **헤더 기반 (대고객과 동일 방식)** - 범위 축소

**결정 변경 이유**: 프로젝트 범위가 너무 커져서 단순화
- Bearer 토큰 방식 제거
- 어드민 계정 관리 API 제거 (슈퍼 어드민용 CRUD)

**유지된 API**:
- 어드민 회원가입 (`/api-admin/v1/admins/signup`)
- 어드민 로그인 (`/api-admin/v1/admins/login`)

**최종 방식**:
- 대고객: `X-Loopers-LoginId`, `X-Loopers-LoginPw`
- 어드민: `X-Loopers-AdminId` (로그인 후 받은 어드민 ID 전달)

**Admin 데이터 모델** (단순화):
- 어드민 ID, 로그인 ID, 비밀번호, 어드민명, 생성/수정/삭제일시

## 세션 2: 요구사항 정리 및 설계 준비 세션

### 논의 1: 기존 코드 패턴 파악

**목적**: 2주차 설계에서 기존 User 도메인과 일관성 있는 구조 유지

**파악한 레이어 구조**:
```
Interfaces (API)     → Controller, DTO, ApiSpec
Application          → Facade (필요시)
Domain               → Entity, Service, Repository(IF), Command
Infrastructure       → RepositoryImpl, JpaRepository
```

**핵심 패턴**:
| 패턴 | 설명 |
|------|------|
| Entity 검증 | `init` 블록에서 즉시 검증 (Fail-Fast) |
| Repository | 도메인에 인터페이스, 인프라에 구현체 |
| DTO 변환 | `toCommand()`, `from()` 메서드 사용 |
| 트랜잭션 | 조회는 `@Transactional(readOnly = true)` |

### 논의 2: 제공된 요구사항 분석

**서비스 개요**: 감성 이커머스
- 브랜드별 상품 탐색 → 좋아요 → 주문 → 결제 흐름

**API 구조 확인**:
| 구분 | Prefix | 인증 헤더 |
|------|--------|----------|
| 대고객 | `/api/v1` | X-Loopers-LoginId, X-Loopers-LoginPw |
| 어드민 | `/api-admin/v1` | X-Loopers-Ldap |

**도메인별 API 정리**:

#### 브랜드 & 상품
- 대고객: 브랜드 조회, 상품 목록/상세 조회
- 어드민: CRUD 전체
- **제약**: 브랜드 삭제 시 상품도 삭제, 상품의 브랜드는 수정 불가

#### 좋아요
- 등록/취소 토글 방식
- 내가 좋아요한 상품 목록 조회

#### 주문
- 대고객: 주문 생성, 기간별 목록 조회, 상세 조회
- 어드민: 전체 주문 목록/상세 조회
- **제약**: 상품 스냅샷 저장 필수, 재고 확인/차감 보장

## 주요 깨달음 / 블로그 포인트

1. **설계 순서의 중요성**: 추상화 수준 높은 것부터 낮은 것 순서로 (What → How)

2. **전제 조건 명확화**: 같은 "이커머스"라도 자사몰/마켓플레이스, 옵션 구조 등에 따라 설계가 완전히 달라짐

3. **요구사항의 모호함을 발견하는 눈**: "이커머스 만들어줘"라는 요구사항에서 결정해야 할 10가지 이상의 선택사항이 숨어있음

4. **누락된 기능 발견**: 요구사항만 보면 놓치기 쉬운 것들 (어드민 인증, 배송비 정책 등)

## 세션 3: 도메인별 요구사항 상세화 (requirements-analysis 스킬 활용)

### 분석 방식
- 각 도메인에 대해 **문제 상황 재해석** → **애매한 요구사항 발견** → **명확화 질문** → **합의** 순서로 진행
- 결정된 사항은 즉시 `ecommerce-requirements.md`에 반영

---

### 논의 1: 브랜드 (Brand) 도메인

**발견된 애매한 요구사항**:
- 브랜드명 중복 허용 여부
- 브랜드 삭제 시 연관 데이터(좋아요, 장바구니) 처리 방식

**결정 사항**:

| 항목 | 결정 | 이유 |
|------|------|------|
| 브랜드명 중복 | **불가** (UNIQUE) | 브랜드 정체성 유지 |
| 삭제 정책 | **연쇄 Soft Delete** | 상품 + 좋아요 + 장바구니 항목 모두 삭제 |
| 수정 범위 | **전체 수정 가능** | 이름, 설명, 로고 모두 |

**연쇄 삭제 흐름**:
```
브랜드 삭제 →
├── 해당 브랜드의 모든 상품 Soft Delete
│   ├── 해당 상품의 좋아요 Soft Delete
│   └── 해당 상품이 담긴 장바구니 항목 Soft Delete
└── 주문 이력은 스냅샷이므로 유지
```

### 논의 2: 상품 (Product) 도메인

**발견된 애매한 요구사항**:
- 상품명 중복 허용 여부
- 옵션 없는 단일 상품 지원 여부
- 재고 0일 때 상태 자동 변경 여부

**결정 사항**:

| 항목 | 결정 | 이유 |
|------|------|------|
| 상품명 중복 | **브랜드 내 불가** | 복합 유니크 (brand_id + name) |
| 단일 상품 | **지원** | 옵션 없이 등록 시 기본 옵션 자동 생성 |
| 재고-상태 연동 | **자동 변경** | 재고 0 → SOLD_OUT, 재고 추가 → ON_SALE |
| 이미지 | **1개만** | 대표 이미지만 등록 |

**단일 상품 처리**:
- 옵션 없이 등록하면 `기본` 옵션이 자동 생성됨
- `additionalPrice = 0`, `stockQuantity = 등록 시 입력한 재고`

---

### 논의 3: 좋아요 (Like) 도메인

**발견된 애매한 요구사항**:
- API 구조 (등록/취소 분리 vs 토글)
- 삭제된 상품의 좋아요 목록 표시 여부
- 좋아요 수 캐싱 여부

**결정 사항 (기존 요구사항과 다른 결정)**:

| 항목 | 기존 | 새 결정 | 이유 |
|------|------|---------|------|
| API 구조 | POST/DELETE 분리 | **토글 API** | 프론트엔드 편의성 |
| 삭제된 상품 | 명시 안 됨 | **목록에 포함** ('삭제됨' 표시) | UX 고려 |
| 좋아요 수 | 명시 안 됨 | **Product.likeCount 필드** | 조회 성능 |

**잠재 리스크**:
- `likeCount` 동시성 문제 → 원자적 증가/감소 쿼리로 해결

---

### 논의 4: 장바구니 (Cart) 도메인

**발견된 애매한 요구사항**:
- 재고 검증 시점 (담기 vs 주문)
- 삭제/품절 상품 처리 방식
- 항목 수 제한

**결정 사항**:

| 항목 | 결정 | 이유 |
|------|------|------|
| 재고 검증 | **담기 시점** | 사용자 즉시 피드백 |
| 삭제/품절 상품 | **유지 + 경고 표시** | 사용자가 직접 삭제 |
| 항목 수 제한 | **없음** | 자유도 확보 |

**장바구니 항목 상태**:
- AVAILABLE: 정상 구매 가능
- OUT_OF_STOCK: 재고 부족
- SOLD_OUT: 옵션 품절
- DELETED: 상품/옵션 삭제됨
- EXPIRED: 유효기간 만료 (조회 시 자동 제외)

---

### 논의 5: 쿠폰 (Coupon) 도메인

**발견된 애매한 요구사항**:
- 동일 쿠폰 중복 발급 허용 여부
- 정률 쿠폰 최대 할인 금액 필수 여부
- 주문 취소 시 쿠폰 복구 여부

**결정 사항**:

| 항목 | 결정 | 이유 |
|------|------|------|
| 중복 발급 | **허용** | 같은 쿠폰 여러 장 보유 가능 |
| 최대 할인 금액 | **필수** | 정률 쿠폰 남용 방지 |
| 적용 범위 | **전체 주문만** | 단순한 구조 유지 |
| 취소 시 복구 | **복구** | 사용자 편의 |

---

### 논의 6: 배송지 (ShippingAddress) 도메인

**발견된 애매한 요구사항**:
- 첫 배송지 자동 기본 설정 여부
- 기본 배송지 삭제 허용 여부

**결정 사항**:

| 항목 | 결정 | 이유 |
|------|------|------|
| 첫 배송지 | **자동으로 기본 설정** | UX 편의성 |
| 기본 삭제 | **불가** | 다른 배송지로 변경 후 삭제 |

### 논의 7: 주문 (Order) 도메인

**발견된 애매한 요구사항**:
- 주문번호 생성 규칙
- 부분 취소 지원 여부
- 부분 재고 부족 시 처리 방식

**결정 사항**:

| 항목 | 결정 | 이유 |
|------|------|------|
| 주문번호 | **ORD-{YYYYMMDD}-{6자리}** | 가독성 |
| 부분 취소 | **미지원** | 단순한 구조 |
| 부분 재고 부족 | **전체 실패** | 일관성 |

### 논의 8: 어드민 (Admin) 도메인

**발견된 애매한 요구사항**:
- 권한 수준(역할) 구분 여부

**결정 사항**:

| 항목 | 결정 | 이유 |
|------|------|------|
| 권한 수준 | **구분 안 함** | 모든 어드민 동일 권한 |

## 주요 깨달음 / 블로그 포인트 (추가)

5. **토글 vs 분리 API**: 좋아요처럼 on/off 성격의 기능은 토글 API가 프론트엔드 친화적

## 세션 4: 설계 문서 작성 세션

### 논의 1: 시퀀스 다이어그램 범위 선정

**질문**: 24개 API 전부 시퀀스 다이어그램 작성해야 할까?

**결론**: 핵심 로직만 작성

**선정 기준**:
- 여러 도메인이 협력하는 복잡한 흐름
- 트랜잭션 경계가 명확해야 하는 흐름
- 동시성/정합성 처리가 필요한 흐름

**선정된 5개**:

| # | API | 선정 이유 |
|---|-----|----------|
| 1 | 주문 생성 | 부분 주문 분기, 비관적 락, 스냅샷 저장 |
| 2 | 좋아요 등록 | 멱등성 분기, Soft Delete 상품 허용, 유니크 처리 |
| 3 | 좋아요 취소 | 멱등성 (없으면 OK), Soft Delete 처리 |
| 4 | 브랜드 삭제 | 연쇄 Soft Delete 범위, 트랜잭션 경계 |
| 5 | 상품 등록 | 브랜드 존재 검증, Soft Delete 브랜드 처리 |

**깨달음**: 텍스트 기반 요구사항이 이미 있으므로, Claude를 위한 도식화가 아닌 **개발자가 이해하기 위한 핵심 흐름**만 작성

### 논의 3: Facade 패턴 도입 이유

**질문**: Service 간 순환 참조되면 뭐가 안 좋아져?

**문제**:
```kotlin
@Service
class BrandService(private val productService: ProductService)

@Service
class ProductService(private val brandService: BrandService)

// → BeanCurrentlyInCreationException 발생
```

**해결**: Facade 레벨에서 조합

```
[잘못된 구조]
BrandService ←→ ProductService (순환 참조)

[올바른 구조]
BrandFacade → BrandService
           → ProductService
```

**원칙**:
- Service는 **단일 도메인 책임**
- 도메인 간 협력은 **Facade 레벨**에서만

### 논의 4: ERD에서 DDL 분리

**질문**: 원래 ERD 작성 시 DDL도 작성해?

**결론**: 분리하는 게 일반적

| 문서 | 내용 | 대상 |
|------|------|------|
| ERD | 다이어그램 + 테이블 설명 | 설계 이해용 |
| DDL/Migration | 실제 SQL 스크립트 | 실행용 |

**이유**: DDL이 두 곳에 있으면 불일치 위험

---

### 논의 5: FK 제약을 실무에서 안 쓰는 이유

**질문**: 보통 실무에서 DB에는 FK 제약 조건 잘 안 걸지 않아?

**FK 안 쓰는 이유**:

| 이유 | 설명 |
|------|------|
| 운영 유연성 | 마이그레이션, 벌크 삽입 시 방해 |
| 성능 | INSERT마다 FK 검증 오버헤드 |
| Soft Delete 충돌 | 삭제된 데이터 참조 시 FK는 통과하지만 의미적으론 삭제 |
| MSA 전환 | 서비스 분리 시 FK 자체가 불가능 |
| 중복 검증 | 어차피 앱에서 검증함 |

**실무 패턴**:
```
FK 제약 없음 → 애플리케이션에서 검증 → 인덱스만 생성
```

**ERD 반영**: FK 표시 제거, "(앱에서 검증)" 명시

## 주요 깨달음 / 블로그 포인트 (추가)

9. **시퀀스 다이어그램 선정 기준**: 모든 API가 아닌, 도메인 협력 + 트랜잭션 경계 + 동시성이 필요한 것만

10. **Facade 패턴의 실용적 이유**: 이론적 장점보다 **순환 참조 방지**가 실무적으로 가장 큰 이유

11. **FK 제약의 현실**: 정석이지만 운영 유연성 + Soft Delete + 앱 검증 중복 때문에 실무에서 안 쓰는 경우 많음

12. **문서의 목적 구분**: ERD는 설계 이해용, DDL은 실행용 - 같은 곳에 두면 불일치 위험
