- 소윤범

  문제 : 재고 차감에 어떤 락을 사용해야할까

  첫번째 멘토링 청강에서 atomic update → 낙관적락 → 비관적락 순으로 우선순위를 두라고 하셨는데, 제 프로젝트는 이미 Read-Modify-Write 구조가 완성된 상태에서 동시성을 고민했기 때문에 atomic update를 제외했고, 낙관적락은 충돌이 잦은 재고 특성상 재시도가 많아져 사용자 경험이 나빠진다고 판단해 비관적 락을 선택했습니다.

  이후 두번째 멘토링 청강에서에서 비관적락의 커넥션 풀 고갈 문제를 인지했고, 현재 규모에서는 문제없다고 판단했지만, 트래픽 증가 시 락 타임아웃 설정이나 Redis 분산 락 전환을 검토해야한다고 생각했습니다.

  돌아보면, 현재 제 프로젝트는 product.reserve() 같은 재고 차감을 도메인 엔티티 메서드로 설계했는데, 이미 Atomic Update 라는 선택지가 닫혔습니다. 동시성 전략은 락 선택이 아니라 도메인 모델 설계 단계에서부터 함께 고민했어야 했다고 생각했습니다.

      **[해결 시도]**

        - 데드락 방지
            - 여러 상품에 동시에 락을 걸 때, 스레드 A가 1→ 2 순서, 스레드 B는 2 → 1 순서로 잡으면 데드락이 발생합니다. productId 오름차순 정렬 후 순차 락을 획득하여 모든 스레드가 동일한 순서로 락을 잡도록 했습니다.
        - 쿠폰 이중 사용 방지 (비관적 락)
            - 비관적 락을 선택했습니다. 낙관적 락은 충돌 발생 시 재시도로 해결하는데, 쿠폰은 재시도가 의미가 없습니다 (이미 다른 트랜잭션이 USED로 변경한 상태에서 재시도해도 결과는 똑같이 실패라고 생각했습니다)
        - 재고 차감 (비관적 락)
            - 재고도 비관적 락을 선택했습니다.

              재고 10개에 20명이 동시에 주문하는 상황으로 생각해보면, 락 없이는 여러 트랜잭션이 동시에 재고를 읽고 모두 재고 있음으로 판단해서 차감해버리는 Lost Update가 발생합니다. 재고가 음수가 되지 않도록 정합성을 최우선해야한다고 생각했고, 실패 시 재시도해도 재고가 부족하면 결국 실패하기 때문에 비관적 락으로 처음부터 순서를 보장했습니다.

      그래서 재고와 주문의 트랜잭션을 분리하고 Exception에 대한 보상 로직을 추가하는 방식으로 구현을 생각해봤습니다.

  그렇게 생각한 이유
  → 주문에 대한 처리는 요청에 독립적이나 재고의 경우는 여러 주문이 동시에 접근할 수 있기 때문에 트랜잭션의 시간을 짧게 가져가면 성능 향상이 될 수 도 있을 것이라고 생각했습니다.

  궁금한 것
  → 이런 식으로 처리하는게 효용성이 있을지 궁금합니다
- 최선강
    - 트랜잭션과 lock의 순서 고려 필요.
        - 트랜잭션 시작 → lock → 트랜잭션 커밋 :  재고 불인치
        - lock 시작 → 트랜잭션 시작 → 트랜잭션 커밋 → lock 해제 : 재고 일치

      좋아요의 따닥 중복 방지는 Unique Constraint로 DB에 위임하고, catch에서 `DataIntegrityViolationException`을 삼켜서 멱등 응답을 보장했습니다. 묶을 연산이 없어 이렇게 @Transactional을 제거했는데 어떻게 생각하시나요?

        ```jsx
        // AS-IS
        class ProductLikeService(
            private val productLikeRepository: ProductLikeRepository,
        ) {
            **@Transactional** 
            fun like(command: LikeProductCommand) {
                productRepository.findByUserIdAndProductId(command.userId, command.productId)?.let {return}
                
                val productLike = ProductLikeModel(command.userId, command.productId)
                productLikeRepository.save(productLike)
            }                                                          
        }
        
        // TO-BE
        class ProductLikeService(
            private val productLikeRepository: ProductLikeRepository,
        ) {
            fun like(command: LikeProductCommand) {
                try {
                    val productLike = ProductLikeModel(command.userId, command.productId)
                    productLikeRepository.save(productLike)
                } catch (e: DataIntegrityViolationException) {
                }
            }                                                          
        }
        ```

            - quantity → 변경 빈도 높음, 쓰기 위주, race condition 발생 → `Atomic Update`(UPDATE ... SET quantity = quantity - :quantity)로 영속성 컨텍스트 우회

- 박수환
    - **재고는 비관적 락, 쿠폰은 낙관적 락**
        - 락 전략을 고를 때 **“모두 성공시켜야 하는가?” vs “1명만 성공하면 되는가?”** 를 기준으로 삼았습니다.
            - **재고·좋아요** → 비관적 락 (`FOR UPDATE`)
                - 여러 유저가 같은 상품에 동시 요청 → **모두 기다렸다가 순서대로 성공**해야 함
            - **쿠폰** → 낙관적 락 (`@Version`)
                - 발급된 쿠폰은 한 유저 소유 → 동시 요청은 같은 유저의 다중 기기뿐
                - **1건만 성공하고 나머지는 실패**시키면 충분

          그런데 쿠폰에서 낙관적 락 충돌이 나면, **주문 트랜잭션 전체가 롤백**되도록 한다면, 이미 차감된 재고까지 되돌려지는데, 클라이언트에게 유효하지 않은 쿠폰이라고만 안내하고 전체 롤백하면 되는걸까요?

        - 그리고 이 도메인별 락 전략 선택 기준이 적절한가요?
    - **DB 비관적 락에서 분산 락으로 전환하는 시점은 언제인가요?**
        - 현재 모든 동시성 제어가 **DB 레벨 락**에 의존합니다.

        ```
        OrderFacade.createOrder()  @Transactional
          ├─ findByIdWithLock()    ← SELECT FOR UPDATE (DB 커넥션 점유)
          ├─ decreaseStock()
          ├─ 쿠폰 검증/사용
          └─ 주문 저장               ← 여기서 커밋될 때까지 커넥션 점유
        ```

      서버가 1대이든 여러 대이든, 같은 DB를 거치므로 동작은 합니다. 하지만 블로그를 쓰면서 실무에서 **DB 커넥션 점유 시간 문제**로 Redis 분산 락으로 전환하는 사례를 다수 봤습니다.

        - **비관적 락이 커넥션 점유 때문에 문제가 되는 시점은 어느 정도 규모인가요?**
        - 분산 락 도입 시 “커밋 후 락 해제” 순서를 보장하기 위해 주로 쓰는 패턴이 있나요?
        - “DB 락으로 충분한 문제에 분산 락을 쓰지 마라”는 의견도 있는데, 전환 기준을 어떻게 잡으시나요?

### 원자적 업데이트 vs 낙관적 락 vs 비관적 락

- **원자적 업데이트**
    - 충돌 가능성이 높을 때
    - 조건 검증 + 상태 변경을 DB에 위임할 수 있을 때
    - 데이터를 애플리케이션에서 읽어 판단할 필요가 없을 때
    - DB가 조건(특정 상황에 도달했을 때부터는 못한다) 검증과 변경을 한 번에 수행
- **비관적 락**
    - 충돌 가능성이 높을 때
    - 동일 데이터에 대한 경쟁이 자주 발생할 때
    - 데이터를 먼저 조회하고, 그 상태를 기반으로 판단해야 할 때
    - 락을 먼저 획득하고 처리
    - 정합성은 강하게 보장하는 대신 처리량은 낮아질 수 있음
- **낙관적 락**
    - 충돌 가능성이 낮을 때
    - 대부분의 요청이 성공할 것으로 예상될 때
    - 먼저 실행하고, 나중에 충돌을 감지
    - *주의: 재시도 하는 것이 낙관적 락이 아님! 실패해도 괜찮을 때 낙관적 락을 써야 함*

### FK를 사용하지 않는 이유

- 가장 큰 이유는 성능
- FK를 쓴다는 것 자체가 개발자가 어플리케이션 단에서 제어를 못 해서 DB 단에서 정합성을 보장하기 위해서 쓰는 것 같음
- 요즘에는 애플리케이션에서 비즈니스를 구성함

### 트랜잭션 분리

- 트랜잭션이 길어지는 문제가 예전에 선배 개발자분들이 고도화된 비즈니스를 개발하면서 가장 먼저 느꼈던 아픔이지 않았을까 그런 것들에 의해서 트랜지션 분리 MSA가 나온 게 아닐까 생각이 듦
- 애플리케이션의 재고를 읽고 계산할 필요 없이 DB 위임으로 충돌을 줄일 수 있었음
- 애플리케이션에서의 재고가 충분한지를 판단할 로직 자체가 삭제됨
- 동시성 이슈 데이터베이스의 동시성 이슈라고 보기는 어렵지만 동시성 이슈를 해결하려면 삽입을 하지만 유니크 컨스트레인트를 활용해서 해결하는 것이 가장 쉬운 방법임

### 재고 처리

- 낙관적 락으로 처리할 거면 재시도를 해야 함
- 비관적 락을 쓰면 재고 테이블을 읽는 게 오래 걸릴 수 있음
- 비정규화를 하거나 테이블을 분리해서 쓰기도 함

### 트랜잭션 관리

- 개인적으로 DB의 트랜잭션을 트랜잭션을 안 믿는 걸 좋아함
- 애플리케이션에서 제어하는 것 추천

### 격리 레벨에 따른 데이터베이스 활용

- 아이솔레이션 레벨에 따라 다르고 데이터베이스에 따라 다름
- 테스트를 해보면 재밌을 것 같음
- 버전에 따라 다르고 명확하게 안 되면 평생 기억에 남으니 꼭 해볼 것

### 비관적 락의 한계

- 데이터베이스의 커넥션 풀을 소중하게 여겨야 된다는 사명감을 안고 달리는 회사에 있다 보니까 비관적 락으로 풀어도 문제 절대 생기지 않는다고 확신할 수 있는 부분에 대해서만 비관적 락을 썼음
- 비관적 락이 부담된다면 아래와 같은 선택지들이 있음
    - 구조 개선
    - 테이블 분리
    - 비정규화
    - 분산 락
    - 아키텍처 변경

### 비관적 락이 커넥션 점유 때문에 문제가 되는 시점

- 명확하게 “TPS가 어느 정도 될 때 이 정도 문제가 됩니다”라고 표현하기는 모호함
- 특정 비즈니스 TPS만 보는 게 아니라 아래 예시들과 같이 DB에 들어가는 모든 쿼리 부하를 고려해야 함
    - 다른 도메인의 조회 쿼리
    - 배치 작업
    - 집계 쿼리
    - 관리성 쿼리
    - 여러 개의 테이블이 하나의 데이터베이스에 몰려 있는지
    - 도메인별로 데이터베이스가 따로 있는지
- 또, 시스템 구조와 트래픽 특성에 따라 달라지므로 직접 부하 테스트를 통해 판단하는 것이 가장 현실적
- 트래픽을 점진적으로 올려보고 지연/타임아웃/에러 발생 지점을 확인하면 “이 수준부터는 위험하다”라고 판단 가능
- 추후 레디스 배운 후 분산락 적용해보면서 분산락은 이정도의 트래픽을 버티는데 비관락은 못 버티더라 라는 감각을 직접 경험해보며 얻으면 좋을 것 같음
