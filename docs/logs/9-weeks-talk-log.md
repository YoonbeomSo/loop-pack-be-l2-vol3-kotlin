## 1. Consumer 결합 방식 — Metrics와 Ranking의 관계

### 고민한 부분
이벤트(조회/좋아요/주문) 소비 시 기존 product_metrics DB 적재와 신규 Redis ZSET 랭킹 적재를 어떻게 연결할 것인가?

### 선택지
- **Option A**: MetricsAggregationService 내부에서 RankingAggregation 호출 (한 곳 관리, 결합 높음)
- **Option B**: Consumer에서 Metrics + Ranking 각각 호출 (독립적 실패 가능, Consumer가 두 서비스 인지)
- **Option C**: 별도 Consumer Group 분리 (같은 토픽을 두 그룹이 각각 소비, 완전 독립)

### 선택한 답
**Option C — 별도 Consumer Group 분리**

### 이유
- 현재 대용량 서비스를 처리한다고 가정하고 학습하는 과정이므로, 실제 대규모 시스템에서의 패턴을 경험하고 싶음
- Kafka를 사용하는 이유 자체가 각 시스템 간의 영향도를 줄이기 위함인데, 이벤트 소비 단에서 다시 결합도를 높이면 Kafka를 쓰는 의미가 퇴색됨
- Metrics 적재 장애가 Ranking에 영향을 주지 않고, 반대도 마찬가지인 구조가 Kafka의 설계 철학과 일치함

### 느낀 점
- 기술 선택의 이유와 일관성 있게 아키텍처를 설계하는 것이 중요하다는 걸 체감
- "이 기술을 왜 쓰는가"에서 출발하면 자연스럽게 결합 방식도 결정됨

## 2. 주문 점수 계산 방식 — 금액 기반 vs 건수 기반

### 고민한 부분
주문 이벤트 발생 시 ZSET에 얼마만큼의 점수를 더할 것인가? 비싼 상품이 항상 유리한 금액 기반 vs 가격 무관한 건수 기반, 그 사이의 로그 정규화 중 어떤 방식이 적절한가?

### 선택지
- **Option A**: `price * quantity * 0.6` (금액 기반) — 매출 기여도 반영, 비싼 상품 압도적 유리
- **Option B**: `log(price * quantity) * 0.6` (로그 정규화) — 가격 차이 완화, 균형
- **Option C**: `1 * 0.6` (건수 기반) — 가격 무관, 순수 인기도

### 선택한 답
**Option A — 과제 가이드대로 `price * quantity * 0.6`으로 우선 진행**

### 이유
- 과제 가이드에 `Score = price * amount` 예시가 명시되어 있으므로 우선 따름
- 단, 점수 계산 로직을 메서드로 잘 분리해서 언제든 정규화 방식으로 교체 가능하게 설계

### 멘토링 질문 (2026-04-08)
- 실무에서 랭킹 점수 계산 시 금액 기반 vs 건수 기반 vs 로그 정규화, 어떤 기준으로 선택하는지?
- 비싼 상품이 항상 상위권을 독점하는 문제를 실무에서는 어떻게 해결하는지?
- 가중치(weight)와 점수(score) 계산을 분리할 때 실무에서 주로 사용하는 패턴이 있는지?

### 느낀 점
- 정답이 명확하지 않은 설계 결정에서 "우선 동작하게 만들되, 교체 가능하게 설계"하는 전략이 실용적이라고 느낌
- 점수 계산 방식은 서비스 전략에 따라 달라지는 부분이라 멘토에게 실무 관점을 확인하고 싶음

## 3. 상품 상세 조회에 랭킹 추가 — 캐시와의 호환 전략

### 고민한 부분
상품 상세 조회(GET /products/{id}) 응답에 순위(rank)를 추가해야 하는데, 기존 ProductCacheService가 ProductInfo를 10분간 캐시하고 있음. 랭킹은 실시간으로 변하므로 캐시에 같이 넣으면 stale한 순위가 노출됨.

### 선택지
- **Option A**: ProductService에서 캐시된 상품 정보 + Redis 순위를 조합해서 반환 (ProductInfo 구조 변경 필요, 캐시에서 rank 제외 처리 필요)
- **Option B**: Controller에서 상품 정보(캐시)와 순위(Redis)를 각각 가져와서 응답에 합침 (기존 캐시 구조 변경 없음)

### 선택한 답
**Option B — Controller 레벨에서 조합**

### 이유
- 기존 캐시 구조를 전혀 건드리지 않아 사이드이펙트가 없음
- 랭킹 조회는 Redis ZREVRANK 한 번(O(logN))이라 충분히 빨라 별도 캐시 불필요
- 상품 정보는 ProductService, 순위는 RankingService로 관심사가 깔끔하게 분리됨
- 1번에서 "Kafka 소비 단에서도 결합도를 낮추겠다"고 한 방향과 일관성 있음

### 느낀 점
- 기존 코드에 새 기능을 추가할 때, "기존 구조를 변경하지 않는 방향"을 먼저 고려하는 습관이 중요하다고 느낌
- 캐시되는 데이터와 실시간 데이터의 성격이 다르면 합치지 말고 조합 시점을 분리하는 게 자연스러움

## 6. ZADD vs ZINCRBY — 왜 ZINCRBY를 썼는가

### 고민한 부분
ZSET에 랭킹 점수를 적재할 때 ZADD와 ZINCRBY 중 어떤 명령어를 써야 하는가?

### 배운 내용
- **ZADD**: 점수를 **덮어쓴다**. `ZADD key 10 member` → `ZADD key 5 member` → 최종 5점
- **ZINCRBY**: 점수를 **누적한다**. `ZINCRBY key 0.1 member` → `ZINCRBY key 0.1 member` → 최종 0.2점
- 이벤트가 올 때마다 점수를 쌓아야 하므로 ZINCRBY가 올바른 선택

### 느낀 점
- Redis 명령어 선택이 곧 비즈니스 로직의 정확성을 결정함
- "덮어쓰기 vs 누적"이라는 단순한 차이지만, 잘못 선택하면 랭킹 데이터 전체가 의미 없어짐

## 7. Ranking Consumer의 멱등성 — 보장해야 하나, 감수해야 하나

### 고민한 부분
기존 Metrics Consumer는 event_handled 테이블로 멱등성을 보장하는데, Ranking Consumer에서는 멱등성 처리를 하지 않았다. ZINCRBY 특성상 같은 이벤트가 2번 소비되면 점수가 이중으로 쌓인다.

### Metrics vs Ranking — 왜 성격이 다른가

| | Metrics | Ranking |
|---|---------|---------|
| 저장소 | DB (영구 저장) | Redis (TTL 2일 후 삭제) |
| 보여주는 것 | "좋아요 42개" (정확한 숫자) | "1위, 2위" (상대적 순위) |
| 오차 누적 | 한번 틀리면 영원히 틀림 | 매일 리셋되므로 오차도 리셋 |
| 중복 1건 영향 | 42개 → 43개 (눈에 보이는 오류) | 순위 변동 가능성 낮음 |

- Metrics는 영구 저장 + 정확한 숫자 노출이라 멱등성이 **필수**
- Ranking은 TTL로 리셋 + 상대적 순위 노출이라 멱등성 없이도 **치명적이지 않을 수 있음**

### 그런데 멱등성을 넣으면?
- 이벤트 1건마다 DB SELECT + INSERT가 추가됨 (비용 증가)
- 별도 Consumer Group이라 기존 event_handled를 공유하면 다시 결합됨
- Ranking 전용 멱등성 테이블이 필요하거나, Redis SET으로 체크하는 방식이 필요

### 멘토링 질문 (2026-04-08)
- 랭킹처럼 TTL로 리셋되는 데이터에도 멱등성을 보장하는 게 실무 기준인지?
- 멱등성 비용(DB 조회) vs 약간의 점수 오차, 실무에서는 어떤 쪽을 택하는지?
- DB 대신 Redis SET(`SADD eventId`)으로 멱등성을 체크하는 패턴이 실무에서 쓰이는지?

### 느낀 점
- "멱등성은 무조건 보장해야 한다"가 아니라, 데이터의 성격(영구 vs 임시, 정확한 숫자 vs 상대적 순위)에 따라 비용 대비 효과를 판단해야 한다는 걸 깨달음
- 하지만 "괜찮을 수도 있다"는 감으로 판단하기보단, 멘토에게 실무 기준을 확인하고 싶음
- 이 고민 자체가 블로그에 쓰기 좋은 주제라고 생각함

## 8. 사용한 Redis 명령어 정리

### 고민한 부분
이번 구현에서 Redis ZSET 명령어를 여러 개 사용했는데, 각각 왜 그 명령어를 선택했는지 정리가 필요했다.

### 배운 내용

**적재 (commerce-streamer):**
- `ZINCRBY` — 이벤트마다 점수 누적. ZADD(덮어쓰기)가 아니라 ZINCRBY(누적)를 쓴 이유는 이벤트가 올 때마다 점수를 쌓아야 하기 때문
- `EXPIRE` — 키에 TTL 설정. 일간 키 2일, 시간 키 3시간. 안 하면 Redis 메모리에 영원히 남음
- `ZRANGEBYSCORE` — Carry-Over Lua 스크립트에서 전일 전체 멤버+점수를 읽을 때 사용
- `ZADD NX` — Carry-Over에서 "이미 점수가 있는 멤버는 건드리지 말고, 없는 멤버만 추가". NX 옵션이 핵심

**조회 (commerce-api):**
- `ZREVRANGE WITHSCORES` — 점수 높은 순으로 Top-N 조회. REV = reverse(내림차순). WITHSCORES로 점수도 함께 가져옴
- `ZREVRANK` — 특정 상품이 몇 위인지 조회. 0-based라서 +1 해서 반환
- `ZCARD` — 전체 멤버 수. 페이징의 totalCount로 사용
- `ZSCORE` — 특정 상품의 점수 조회 (인터페이스 정의만 해두고 아직 미사용)

### 흐름 정리

```
[적재] 이벤트 → ZINCRBY(점수 누적) → EXPIRE(TTL 설정)
[조회] API → ZREVRANGE(Top-N) + ZCARD(전체 수) → 상품 정보 조합 → 응답
[상세] API → ZREVRANK(개별 순위) → 상품 상세에 rank 추가
[Carry-Over] 스케줄러 → ZRANGEBYSCORE(전일 읽기) → ZADD NX(다음날 복사) → EXPIRE(TTL)
```

### 느낀 점
- ZSET 하나로 적재/조회/순위/카운트까지 전부 가능해서 랭킹에 최적화된 자료구조라는 걸 체감
- 각 명령어의 옵션(NX, REV, WITHSCORES)이 비즈니스 요구사항과 직접 연결됨
- MySQL로 이걸 하려면 `GROUP BY + ORDER BY + COUNT`를 매번 돌려야 하는데, ZSET은 삽입 시점에 이미 정렬되어 있어서 조회가 빠름

## 9. 랭킹 데이터 DB 동기화 필요성 — Redis만 SoT로 두면 괜찮은가? (멘토링 피드백)

### 멘토링에서 나온 질문
> "현재 Redis를 SoT(Source of Truth)로 두고 Kafka 컨슈머가 일별 ZSET에 메트릭을 적재하는 구조인데,
> 배치를 통해 Redis 메트릭을 DB에 주기적으로 동기화하면 불필요한 복잡도인지, 적절한 수준인지?"

### SoT란?
- Source of Truth = "진짜 데이터가 어디에 있냐"
- 우리 랭킹은 Redis ZSET이 유일한 저장소 → Redis가 SoT

### 문제 인식
현재 구조에서 Redis가 죽으면 랭킹 데이터가 전부 유실됨.

```
현재:     Kafka → Consumer → Redis ZSET (유일한 저장소)
                                └── Redis 죽으면? → 데이터 전부 유실

DB 동기화: Kafka → Consumer → Redis ZSET
                                └── 배치로 주기적 DB 동기화 (백업)
                                      └── Redis 죽어도 DB에서 복구 가능
```

### 트레이드오프

| | Redis만 (현재) | DB 동기화 추가 |
|---|--------------|--------------|
| Redis 정상 | 문제 없음 | 문제 없음 |
| Redis 장애 | 랭킹 데이터 전부 유실 | DB에서 복구 가능 |
| 구현 복잡도 | 단순 | 배치 잡 + 동기화 로직 추가 |
| 데이터 성격 | TTL 2일, 어차피 사라짐 | DB에 이력 남길 수 있음 |

### 고민 포인트
- TTL 2일이라 "어차피 사라지는 데이터"인데 DB 백업까지 필요한가?
- 반대로 Redis 장애 시 빈 랭킹이 유저에게 노출되면 서비스 품질 문제
- "배치 동기화가 적절한 수준인지 vs 불필요한 복잡도인지"는 서비스 규모와 장애 허용 수준에 따라 다름

### 느낀 점
- Redis를 유일한 저장소로 쓸 때 "장애 시 복구 방안"을 항상 함께 고민해야 한다는 걸 깨달음
- 캐시로 쓸 때는 DB가 원본이니 괜찮지만, SoT로 쓸 때는 얘기가 다름
- 이 관점은 랭킹뿐 아니라 Redis를 주 저장소로 쓰는 모든 설계에 적용되는 주제

## 10. 가중치 변경의 어려움 — Feature Flag와 A/B Test (멘토링 피드백)

### 멘토링에서 나온 질문
> "랭킹 가중치를 바꿔야겠다고 판단한 뒤, 실제로 변경을 반영하는 과정에서 어려움이 있었는지?"

### 현재 우리 코드의 한계
```kotlin
// RankingScorePolicy.kt
companion object {
    const val VIEW_WEIGHT = 0.1    // 코드에 상수로 박혀있음
    const val LIKE_WEIGHT = 0.2    // 바꾸려면 코드 수정 + 빌드 + 배포
    const val ORDER_WEIGHT = 0.6
}
```
가중치를 바꾸려면 **코드 수정 → 빌드 → 배포**가 필요함. 빠르게 실험하거나 롤백하기 어려움.

### 멘토가 제시한 방향: Feature Flag + A/B Test

**Feature Flag** — 기능을 코드에 넣어두되, 외부 설정으로 켜고 끌 수 있게 하는 것
- 가중치를 외부 설정(DB, Redis, 어드민 등)에서 읽어오면 배포 없이 즉시 변경 가능
- 버그 발견 시 즉시 이전 값으로 롤백

**A/B Test** — 두 가지 버전을 동시에 돌려서 데이터로 비교
- 유저 A그룹(50%): 기존 가중치 `price × qty × 0.6`
- 유저 B그룹(50%): 신규 가중치 `log(price × qty) × 0.6`
- 2주 후 클릭률, 구매 전환율 비교 → 데이터로 결정

### 핵심 깨달음
- 가중치 같은 비즈니스 파라미터는 "감으로 정하는 게 아니라 데이터로 검증"하는 것
- 그러려면 코드에 상수로 박아두면 안 되고, 외부에서 변경 가능한 구조가 필요
- Feature Flag → A/B Test → 데이터 기반 의사결정, 이 흐름이 실무에서의 표준 패턴

### 느낀 점
- 처음에 "메서드로 잘 분리해서 교체 가능하게"라고 생각했는데, 그건 개발자가 코드를 수정하는 수준이었음
- Feature Flag는 그보다 한 단계 위 — 비개발자(PM, 데이터분석가)도 가중치를 조절할 수 있는 구조
- 당장 구현하진 않더라도, 이런 확장 방향이 있다는 걸 아는 것 자체가 중요

## 11. 조회수 어뷰징 방지 — 전략 설계 과정

### 고민한 부분
랭킹 점수에 조회수(view × 0.1)가 반영되는데, 봇이나 악의적 유저가 반복 조회로 특정 상품의 순위를 조작할 수 있다. 어떻게 방어할 것인가?

### 검토한 전략과 판단

#### Layer 1: userId/IP 기반 일간 중복 제거 (채택)
```
로그인 유저 → userId + productId 하루 1회만 반영 (IP 무시)
비로그인 유저 → IP + productId 하루 1회만 반영
판단 우선순위: userId 있으면 userId로, 없으면 IP로
```
- Redis key: `ranking:view:dedup:{yyyyMMdd}:{productId}:user:{userId}` or `:ip:{ip}`
- TTL 1일
- 같은 IP여도 로그인 유저끼리는 각각 반영 (회사 와이파이 문제 해결)
- **채택 이유**: 구현 간단, 같은 사람의 반복 조회를 확실히 차단

#### Layer 2 후보 1: 상품 단위 감쇠 점수 (미채택)
- 한 상품에 조회가 몰릴수록 1건당 점수가 줄어드는 방식
- 1~500건: 100%, 501~1000건: 50%, 1001건~: 25%, 2001건~: 0%
- **미채택 이유**: 이벤트나 세일로 진짜 트래픽이 몰릴 때도 감쇠됨. 정상 트래픽과 어뷰징 트래픽을 서버 입장에서 구분 불가능.

#### Layer 2 후보 2: 후속 행동 기반 가중치 (아이디어만)
- "조회만 하고 떠나는 유저"는 봇일 가능성 높음
- 조회 후 좋아요/주문 등 후속 행동이 있으면 정상, 없으면 낮은 가중치
- **미채택 이유**: 구현 복잡도 높음. 후속 행동을 기다려야 해서 실시간 반영이 어려움

#### Layer 2 후보 3: 조회 속도 감지 (미채택)
- 같은 식별자에서 1초 내 연속 조회 시 skip
- **미채택 이유**: Layer 1에서 하루 1회로 이미 잡고 있어서 추가 효과 미미

#### Layer 2 후보 4: User-Agent 필터 (미채택)
- 브라우저가 아닌 요청(python-requests, curl 등) 차단
- **미채택 이유**: User-Agent는 문자열 하나 바꾸면 위조 가능. 어뷰징을 의도한 봇이 User-Agent를 안 바꿀 리 없음. 단순 스크립트 봇은 잡을 수 있지만 Layer 1에서 이미 걸림.

### 최종 결정
**Layer 1(userId/IP 중복 제거)만 구현. Layer 2는 미적용.**
- Layer 1만으로 같은 사람/IP의 반복 조회는 확실히 차단
- IP 우회(VPN 등) 어뷰징은 Layer 1에서 못 막지만, 현실적으로 비용이 높은 공격
- Layer 2 후보들은 모두 "진짜 트래픽을 해칠 수 있다"는 공통 문제가 있었음

### k6 테스트 시나리오
| # | 시나리오 | 검증 |
|---|---------|------|
| 1 | 같은 유저 같은 상품 100회 | 1회만 반영 |
| 2 | 같은 IP 다른 로그인 유저 10명 | 10명 모두 반영 |
| 3 | 비로그인 같은 IP 100회 | 1회만 반영 |
| 4 | 같은 유저 다른 IP | userId 기준이라 1회만 반영 |

### 느낀 점
- 어뷰징 방지는 "완벽한 차단"이 목표가 아니라 "합리적인 수준의 방어"가 목표
- 모든 Layer 2 전략이 "진짜 트래픽도 해칠 수 있다"는 부작용이 있어서, 트레이드오프 판단이 핵심
- 블로그에는 "검토했지만 적용하지 않은 이유"를 쓰는 게 "구현했다"보다 더 좋은 글이 될 수 있음
- 실무에서도 완벽한 방어는 불가능하고, 데이터 사이언티스트가 복잡한 모델을 만드는 이유가 여기에 있음

## 12. 빅테크의 어뷰징 방지 전략 조사

### 조사 내용
YouTube, Google Ads 등 빅테크의 조회수/클릭 사기 방지 시스템을 조사했다.

### YouTube 조회수 검증 (다층 방어)
- **Layer 1 (기본 필터)**: 같은 IP 반복 조회 감지, 30초 미만 시청 미반영, Device Authentication
- **Layer 2 (패턴 인식)**: "수백 개 계정이 정확히 30초만 시청 후 이탈" → 봇 판단. 조회 대비 좋아요/댓글 비율 분석
- **Layer 3 (머신러닝)**: 봇 패턴을 학습한 ML 모델이 실시간 판단. 96% 이상의 인공 트래픽 식별

### Google Ads 클릭 사기 방지
- **Layer 1**: IP 추적 + Device Fingerprinting, 같은 기기/IP 반복 클릭 차단
- **Layer 2**: 클릭 후 체류 시간, 페이지 이동 패턴 분석
- **Layer 3**: 수십억 클릭 데이터로 학습한 ML 모델

### 공통 패턴
빅테크도 Layer 1(중복 제거)은 기본. Layer 2(행동 분석)와 Layer 3(ML)은 데이터 사이언스 영역.
핵심 인사이트: "차단이 아니라 신뢰도 기반 차등 반영"이 진짜 트래픽을 해치지 않는 방법.

### 느낀 점
- 우리가 하려는 userId/IP 중복 제거는 빅테크에서도 기본으로 까는 정석
- 빅테크의 Layer 2 핵심은 "행동 분석" — 조회만 하는지, 후속 행동이 있는지
- ML 없이도 "다중 시그널 기반 신뢰도 점수"로 유사한 효과를 낼 수 있다는 아이디어를 얻음

## 13. Layer 2 설계 — 신뢰도 기반 점수 차등 (Trust Score)

### 발상의 전환
기존: 정상이면 반영, 비정상이면 차단 (이진적)
새로운 접근: **얼마나 신뢰할 수 있는 조회인가?** (연속적)

→ 차단하지 않되, 신뢰도에 따라 반영되는 점수가 달라진다.
→ 진짜 트래픽은 풀 점수, 의심 트래픽은 낮은 점수, 봇은 거의 0점.

### 신뢰도 시그널 5가지

| # | 시그널 | 정상 | 의심 | 측정 방법 |
|---|--------|------|------|----------|
| 1 | 로그인 여부 | 로그인 | 비로그인(guest) | userId 존재 여부 |
| 2 | 계정 연령 | 7일 이상 | 1일 미만 (신규) | 가입일 기준 |
| 3 | UA/Referer 존재 | 있음 | 없음 | HTTP 헤더에서 추출 |
| 4 | 분당 요청 수 | 1~3회 | 10회 이상 | Redis 카운터 |
| 5 | 10분 내 다른 상품 조회 수 | 여러 상품 탐색 | 한 상품만 반복 | Redis SET |

### 신뢰도 → 점수 배수

```
정상 로그인 유저:  Trust Score = 1.0  →  0.1 × 1.0 = 0.1점
정상 비로그인:     Trust Score = 0.3  →  0.1 × 0.3 = 0.03점
의심 트래픽:       Trust Score = 0~0.1 → 0.1 × 0.1 = 0.01점
```

### 효과 비교

```
봇이 신규 계정 100개로 조회:   100 × 0.1 × 0.1 = 1점
정상 유저 100명이 조회:         100 × 0.1 × 1.0 = 10점
→ 같은 100건이어도 10배 차이
```

### 왜 진짜 트래픽을 해치지 않는가
- 정상 로그인 유저는 ×1.0 → 이벤트로 몰려도 풀 점수
- 비로그인도 ×0.3 → 반영은 되지만 낮은 가중치
- 봇은 여러 시그널에서 낮은 점수 → 하나만 위조해도 나머지에서 걸림

### k6 테스트로 검증할 것
| # | 시나리오 | 기대 결과 |
|---|---------|----------|
| 1 | 정상 로그인 유저 100명 | 상품A 점수 = 10점 |
| 2 | 봇 신규 계정 100개 | 상품B 점수 = 1점 (10배 차이) |
| 3 | 비로그인 정상 유저 100명 | 상품C 점수 = 3점 |
| 4 | 혼합 (정상 50명 + 봇 50개) | 정상 시그널이 지배적 |

### 느낀 점
- "차단 vs 허용"의 이진적 사고에서 벗어나 "신뢰도 기반 차등"이라는 연속적 접근이 핵심
- YouTube 등 빅테크의 행동 분석을 ML 없이 "규칙 기반 다중 시그널"로 근사할 수 있다는 아이디어
- 이 설계 과정 자체가 블로그의 가장 좋은 소재 — "왜 이런 구조를 선택했는가"

## 14. k6 어뷰징 테스트 — 실행 가이드 및 기대 결과

### 실행 방법
```bash
# 1. Docker 인프라 실행
docker-compose -f docker/infra-compose.yml up -d

# 2. commerce-api 실행 (8080)

# 3. commerce-streamer 실행 (다른 터미널, 포트 8082)
./gradlew :apps:commerce-streamer:bootRun --args='--server.port=8082'

# 4. 테스트 상품 3개 생성 (어드민 API)
# 5. k6 실행
k6 run k6/ranking-abuse-test.js
```

### 테스트 시나리오
| 시나리오 | VU | 반복 | 대상 상품 | 특징 |
|---------|-----|------|---------|------|
| normal_users | 100 | 3회/VU | 상품1 | 로그인 + UA + Referer |
| bot_single_ip | 1 | 100회 | 상품2 | 비로그인, 50ms 간격 |
| bot_multi_ip | 100 | 1회/VU | 상품3 | 비로그인, UA/Referer 없음 |
| mixed | 50 | 2회/VU | 상품1+3 | 정상+봇 혼합 |

### 기대 결과
```
상품1 (정상 유저 100명 × Trust 1.0):
  Layer 1: 100명 통과 (각각 다른 userId)
  Layer 2: Trust Score ≈ 1.0 (로그인 + UA + Referer + 다양한 상품)
  예상 점수: 100 × 0.1 × 1.0 = 10.0점

상품2 (단일 IP 봇 100회):
  Layer 1: 1회만 통과 (같은 IP)
  Layer 2: Trust Score ≈ 0.05 (비로그인 + 단일 상품)
  예상 점수: 1 × 0.1 × 0.05 = 0.005점

상품3 (다중 IP 봇 100개):
  Layer 1: 100회 통과 (k6 VU는 같은 IP지만 비로그인 → IP 기준 1회만)
  Layer 2: Trust Score ≈ 0.05 (비로그인 + UA 없음)
  예상 점수: 1 × 0.1 × 0.05 = 0.005점

결론: 상품1(10.0) >> 상품2(0.005) ≈ 상품3(0.005)
      정상 유저 타겟이 봇 타겟보다 2000배 높은 점수
```

### 실행 시 주의사항
- commerce-api와 commerce-streamer가 **같은 포트(8080)로 시작하지 않도록** 주의
- Streamer는 `--server.port=8082` 옵션 필수
- 테스트 전 Redis 데이터 초기화 권장: `docker exec redis-master redis-cli FLUSHALL`
- k6 테스트 후 Consumer 처리 시간(3~5초) 대기 필요

### 실제 k6 실행 결과 (2026-04-10)

```
1위: 상품1 (score: 0.4000) ← 정상 로그인 유저 5명 × 2회
2위: 상품3 (score: 0.0550) ← 비로그인 봇 5개 (UA 없음)
3위: 상품2 (score: 0.0450) ← 단일 IP 봇 10회 반복
```

| 상품 | 시나리오 | 요청 수 | 점수 | 정상 대비 |
|------|---------|--------|------|----------|
| 상품1 | 정상 로그인 5명 | 10회 | 0.4000 | 100% |
| 상품3 | 비로그인+UA없음 5개 | 5회 | 0.0550 | 14% |
| 상품2 | 단일 IP 봇 | 10회 | 0.0450 | 11% |

**결론: 봇이 10회 조회해도 정상 유저 5명의 11% 수준. 어뷰징으로 순위 조작 사실상 불가능.**

### 10x 스케일 테스트 결과

```
1위: 상품1 (score: 4.0000) ← 정상 로그인 유저 50명 × 2회
2위: 상품2 (score: 0.0550) ← 단일 IP 봇 100회 반복
3위: 상품3 (score: 0.0450) ← 비로그인+UA없음 봇 50개
```

| 상품 | 시나리오 | 요청 수 | 점수 | 정상 대비 |
|------|---------|--------|------|----------|
| 상품1 | 정상 로그인 50명 | 100회 | 4.0000 | 100% |
| 상품2 | 단일 IP 봇 | 100회 | 0.0550 | 1.4% |
| 상품3 | UA없는 봇 50개 | 50회 | 0.0450 | 1.1% |

**스케일 비교:**
- 1x: 봇이 정상의 11~14%
- 10x: 봇이 정상의 1.1~1.4%
- 정상 유저가 늘어날수록 봇의 영향력은 더 줄어든다 (선형 vs 고정)

**핵심: 봇 점수는 Layer 1에서 1회로 제한되어 고정, 정상 유저 점수는 인원에 비례해 증가**
